# Pass 1 — Bug Hunt

## Method
0. **Find the copy that actually executes — FIRST, before reading anything.** (Hoisted to a *universal* Phase-0 precondition in `SKILL.md` — it now runs for **every** engagement, not only the bug hunt, because a perf/token/delivery pass that profiles, slims, or rewrites the wrong copy wastes the pass just as badly.) A skill's `scripts/` copy is often **not** the one that runs. A `no_agent` cron with `profile` unset resolves `script: foo.py` under `~/.hermes/scripts/foo.py`, not the skill dir — and the two copies drift, so the live bug lives in the copy you're *not* looking at. (In one tune-up, parallel reviewers audited the skill-dir copy while the cron ran a divergent `~/.hermes/scripts/` copy — half the "bugs" were in dead code.) Determine the live path from the job config (`hermes cron list` / `~/.hermes/cron/jobs.json` → `script` + `profile`), `diff` it against the skill-dir copy, and review the executed one. If they differ, that divergence is itself bug #1 — consolidate to a byte-identical copy.
1. **Read everything:** SKILL.md, every file under `scripts/`, and the script's *dependencies* (shared renderers, the data file it reads, any sibling skill it calls). Read the data file's real shape — don't assume the schema.
2. **Run the auditor** (`scripts/skill_audit.py`) for the mechanical smells.
3. **Validate against LIVE data — this is non-negotiable.** Every confirmed bug in the source tune-up was found by *running* the code, not by reading it:
   - Run any dry/read-only mode (`--json`, `--dry-run`) against the real data file and eyeball the output.
   - Import the script with `importlib` and call its pure functions on **synthetic edge cases** (unknown enum value, missing optional field, `null`/empty field, future/past dates).
   - Confirm counts/IDs/ordering match what the SKILL.md promises.
4. **For logic that's hard or destructive to trigger live, validate it deterministically in isolation — "ran the dry mode, looked fine" is not proof.** A conflict/upsert policy, a retry/backoff state machine, or a correction that only fires under a rare condition won't be exercised by a normal dry run. Drive the exact path under your control: **clone the DB to a temp file** and feed it the conflicting rows one at a time (e.g. prove an `ON CONFLICT` upsert *fills* a NULL, *never inflates*, and *never wipes* a good value); or **stub the I/O layer and assert the recorded side-effects** (replace the HTTP call with a scripted status sequence and check the backoff *sleeps* the retry loop actually performs, that 429 honors `Retry-After`, that 404 doesn't retry). (spotify-playlist-refresh: both the self-correcting upsert and the 429/5xx retry machine were proven this way before shipping — neither is reachable against the live API on demand.) This is also how you validate a fix whose trigger you can't reproduce live.

## Bug-class checklist (each was a real finding)
- **Silent data drop on unrecognized values.** Code that iterates a fixed allow-list (`for cat in CATEGORY_ORDER`) and drops anything else — the item vanishes from output *and* shifts every downstream index/number. Fix: append unknowns (with a warning), never drop silently.
- **`KeyError` on a missing optional field.** `d["interval_days"]` vs `d.get("interval_days", DEFAULT)`. One absent field shouldn't crash the whole run.
- **Swallowed subprocess failure.** `subprocess.run(...)` whose `returncode` is never checked → the script prints "done" and exits 0 even though delivery failed. Brutal for cron. Fix: check `returncode`, log `stderr`, exit non-zero.
- **Uncaught `TimeoutExpired`.** `subprocess.run(timeout=N)` raises on slow children; if uncaught it crashes mid-run (looks like a hang). Catch it and degrade cleanly.
- **Premature cleanup.** Deleting a generated artifact (image/temp file) before confirming it was consumed/delivered — a failed send then can't be retried. Only clean up confirmed-successful outputs.
- **Dead / untested code.** A function never called from the live path (e.g. a write helper in a read-only script) rots and misleads. Remove it or wire it up; don't ship untested logic.
- **Unguarded file load.** `json.load(open(path))` with no `try/except` → a missing/corrupt file dumps a traceback. Guard it and exit with a clear message.
- **Time recomputed per call.** `date.today()` called in several places → values disagree across a midnight boundary. Compute `today` once and thread it through.
- **Negative durations from clock skew.** Subtracting dates without clamping → `-1d` displays when the device clock lags. Use `max(0, …)`.
- **Shared helper silently emits wrong-but-plausible output.** A formatter/renderer that *tolerates* a contract violation instead of rejecting it ships a believable-but-wrong artifact with no warning — e.g. a table renderer fed 6 values under 7 headers shifts every column (a cost lands under "Cache Write") yet still produces a clean image. Fix: make shared helpers **fail loud** on contract violations (`raise ValueError` on header/row-width mismatch), so caller drift surfaces instead of shipping silently.
- **Empty-string normalization → false-equality merge.** A normalizer that returns `""` for empty input (`normalize_url("") == ""`) makes two *different* records with empty keys compare equal — so a dedupe/cluster step merges unrelated items, and any count built on it inflates (here two URL-less articles merged and fabricated a "2 sources" corroboration signal that promoted them to must-read). Fix: require the key be non-empty before treating equality as a match.
- **`except` narrower than the failures that occur.** `except requests.RequestException` does **not** catch the `KeyError`/`IndexError`/`json.JSONDecodeError` raised when parsing a **malformed-but-HTTP-200** response (error envelope, empty `choices`) — so it escapes the retry loop and the retry hardening never fires for the case it was built for. Fix: catch the parse/shape errors too, or have the extractor return a sentinel the retry treats as "empty".
- **Unbounded producer vs a hard downstream limit.** Output with no length cap (an LLM summary, a user string) meeting a hard external limit (Discord's 2000-char message) fails at the boundary. Fix: cap/truncate before the boundary; don't assume the producer stays small.
- **Substring / priority-order shadowing.** A broad match tested before a specific one swallows it — an emoji map doing `if "rain" in t: …` with the `heavy` check *after* rendered **"Heavy Rain" as *light* rain**, and the heavy branch was unreachable for any rain/shower text. The tell is a never-reached specific branch. Fix: order specific-before-generic (test `"heavy rain"` / `"thundery"` before the bare `"rain"`).
- **Provider-fallback order silently rides on the primary's failure modes.** `try A, then B` often "works" only because A happens to *fail* for the input class B handles best. `geocode()` tried Google→OneMap; a *separate* `KeyError` made Google always throw, so OneMap (richer SG addresses) won by accident. Fixing Google's bug made it succeed first and **silently demoted output quality** (building name → terse "Singapore <postal>"). Fix: order providers by *who gives the best answer for this input class* (postal → OneMap first), not incidental fall-through — and re-check output quality after you fix the primary.
- **A rate-limit / error body that mimics empty data.** A 429 or 5xx whose JSON is shaped like a valid-but-empty payload (`{"code":24,"name":"TOO_MANY_REQUESTS","data":null}`) is indistinguishable from "no results" to a `want()` / shape predicate — so the symptom surfaces as *"section unavailable / no data,"* not *"rate limited,"* and you debug the parser instead of the limit. Fix: check the **HTTP status**, not just the body shape; treat 429/5xx distinctly (back off, surface "rate limited"). (sg-commute: a back-to-back run tripped data.gov.sg's ~5-req/10s anon limit and reported "Air Quality unavailable".)
- **An uncaught exception in a `no_agent`, stdout-delivered script posts its *traceback* to the channel.** The cron auto-deliver treats stdout as the message body, so a `KeyError` on an empty API response delivered a Python stack trace to Discord verbatim. Fix: wrap a top-level guard that logs the error to **stderr** and emits a minimal valid message (or nothing) on stdout — never let a traceback reach the delivery surface.
- **An incremental cursor advanced only over *successes* mishandles deterministically-skipped items.** A watermark computed as `max(timestamp of successfully-processed items)` never passes an item that was *intentionally* skipped (a parse failure, a filtered record) but sits **newer** than the last success — so its "report once" side-effect (a Discord alert) re-fires **every run**, and an all-skipped run advances nothing at all. Fix: advance the cursor over **every item you deterministically handled** — successes *and* permanent skips — bounded strictly below the earliest *retryable* failure (a fetch error you *do* want to retry). The mirror failure is a skip that's *too quiet*: an `except: continue` that drops a real item (an empty/garbage upstream field) with no tally looks like a clean run — **count every skip and surface the count** so systemic upstream breakage announces itself. (foodpanda: a parse-failure alert re-fired nightly because `parse_failures` held only msg-ids, not timestamps, so it was excluded from the watermark; separately, empty `Date` headers were dropped silently until a counted `⚠️ Unreadable Email Dates` alert was added.)
- **A window query reads only the *current* partition when the window can span two.** Data partitioned per period (a sheet tab per month, a table per day) but queried by a sliding window (Mon–Sun) silently drops the slice of the window living in the neighbouring partition — undercounting near every boundary (here ~monthly). The tell: totals look right mid-period and wrong right after a rollover. Fix: when `partition(window_start) != partition(window_end)`, read **both** and merge before filtering. (foodpanda: the weekly report read only the current-month tab, so a week straddling month-end lost the previous month's days from the weekly total.)
- **"Not-found" conflated with "hard error" → a spurious alert for a benign normal state.** A read that *raises* for a resource that simply doesn't exist yet (a month tab created lazily on first write) gets caught by a generic `except` and posted as an error — so the *normal* start-of-period state pages a human every time. Fix: detect the specific not-found signal (match the API's error string, e.g. Sheets' `Unable to parse range`) and treat it as empty; only alert on genuine failures. (The inverse of the rate-limit-mimics-empty class above: there an *error* was read as empty; here *empty* is read as an error.)
- **`[^X]*` "skip-until-X" character class breaks when X can legitimately appear in the skipped span.** `Order total[^S]*S\$` is meant to walk to the first `S$`, but it stops dead at any earlier capital `S` ("Service", "Singapore", "SGD") — so an ordinary receipt fails to parse and falls into the skip path. Fix: use non-greedy `.*?` (`Order total.*?S\$`) to reach the real delimiter; reserve negated classes for delimiters that genuinely cannot occur in the span.
- **Implementation contradicts a hard requirement its own SKILL.md declares.** SKILL.md said in bold "⚠️ ALWAYS use `format=png32`" (PNG8 silently drops the overlay in Discord), yet the canonical script never set `format` and shipped the default PNG8 — the skill violated its own mandatory rule, and the SKILL.md *example* even set it while the script it points to didn't. Fix: cross-check **every** MUST/ALWAYS/REQUIRED imperative in SKILL.md (and the doc's own code example) against the executed code; a bolded rule with no matching line in the script is the tell. (google-route-map)
- **Code contradicts its docs/config — but the *code* may be the deliberate, correct side.** The mirror of the class above: when code and docs disagree, don't reflexively "fix" the code to match the doc — the divergence can be an intentional, hand-tuned change nobody wrote down. (spotify-playlist-refresh: `scorer.py` hardcoded a 7-day window + 7-day half-life while `config.yaml` *and* SKILL.md said 30/14 — but a linked diagnosis doc had *recommended* the 7-day change, so the **code was right and the docs were stale**; "fixing" the code back to 30/14 would have undone a deliberate tune.) Fix: before editing, establish which side is canonical (changelog, linked design/decision docs, git, or **ask the user when it's a genuine preference**) and reconcile toward the *intended* behavior — then make the value a live config knob (defaults = current values) so the two can't drift again. **Behavioral / ranking / scoring parameters are usually the user's call** — surface options, don't silently retune.
- **HTTP 2xx ≠ a valid payload — especially for binary/file output.** Google Static Maps returns **HTTP 200 with an error *image*** for some failures (and `urlopen` *raises* on 4xx, uncaught → traceback); the script wrote whatever bytes came back and printed "Saved …", announcing a success it never verified. Fix: confirm the response is the thing you asked for — check `Content-Type` **and** the magic bytes (`data.startswith(b"\x89PNG\r\n\x1a\n")`) before writing/reporting, and wrap the call in `try/except HTTPError/URLError` with a `timeout`. (The file-output cousin of the malformed-200 and rate-limit-mimics-empty classes above: there a bad body read as "empty"; here "bytes were written" masquerades as "it worked".)
- **A configured default / constant that violates the external API's documented input limit.** `make_static_map_url(size="700x450")` exceeded Static Maps' 640-px-per-dimension cap, so the **default** invocation always returned HTTP 400 — and the SKILL.md example used a *legal* `600x400`, i.e. the code had drifted from its own doc. Fix: check every hardcoded request parameter against the API's documented limits, not just the values the doc happens to show; a `scale`/`size`-style multiplier does **not** raise the base cap.
- **A table and a map that disagree on label numbering — but share the same data.** `print_table` used raw `enumerate(i)` (numeric) while `build_map_url` used A-Z for indices 10-35 — same script, same cameras, two different label schemes. The user cannot correlate row `#10` to marker `A`. The tell is a shared data source feeding two renderers with independent label logic. Fix: make a single `marker_label(i)` source of truth used by both. (traffic-camera: the region-map skill's table and map disagreed on every region with ≥10 cameras; a shared `marker_label()` function unified them. Found by the fan-out, not the author.)
- **A limit the code *measures* but never *enforces*.** The script computed and printed `len(url)` against the ~8 KB Static Maps ceiling, then proceeded regardless — the metric was surfaced, the guard was missing. Tell: a printed/logged threshold value with no `if … : abort` beside it. (A focused case of unbounded-producer-vs-hard-limit; the fix is to act on the number you already have.)
- **Hardcoded secret in skill files.** A live Google API key was embedded in the script **and** duplicated verbatim in `SKILL.md`. Fix: read it from `GOOGLE_API_KEY` / `~/.hermes/.env`, never a literal; **rotate** any key ever committed; after scrubbing, `grep` *every* file in the skill for the key pattern (it's easy to fix the script and miss the copy in the doc).
- **Doc↔code drift, and a doc example that breaks the doc's own rule.** SKILL.md claimed `1200×800` output while the code produced `1400×900`; documented "red A/B" markers were green-H/red-W in code; and the Step-2 example interpolated **unencoded** `{FROM_PLACE}` even though the Tips section demanded every value be URL-encoded. Fix: re-derive the doc's stated dimensions/labels/examples from the actual code each pass, and check the doc isn't self-contradictory. (Distinct from Step 0's *copy↔copy* drift — this is *doc↔code*.)
- **A defense that exists but is *dead* below an earlier unconditional `return` in an ordered short-circuit pipeline.** A categorizer/router that runs gates top-to-bottom and `return`s on the first match can have a protection added at the *bottom* (a "rescue" default) that is silently unreachable for inputs an earlier branch already claims. The guard is present in the source — it reads as correct on a skim — but never executes for the case it was meant to protect. (email-gmail-triage: the "a real human is never auto-filed → default to Action" rescue sat at the end of `categorize()`, but a promo/receipt **subject-keyword** branch above it returned `Auto-filed` first, so a known human's "Weekly update" / "Invoice" / "offer" mail was archived — and the SKILL.md explicitly said "never apply `offer` as a standalone signal".) Tell: a guard whose job is to *prevent* an outcome, sitting below a branch that can *produce* that outcome. Fix: trace **every** early `return` and ask "does a later guard need to run before this fires?"; hoist the protective check above the branches it must veto. (The protective cousin of *substring/priority-order shadowing* — there a broad classification shadows a specific one; here a broad action shadows a safeguard — and an instance of *implementation-contradicts-its-own-SKILL.md*.)
- **A periodic "remind me about outstanding X" job built from the current run's items instead of the live backlog.** A reminder/digest that reuses the list of items *this run just processed* only ever surfaces things that happened to arrive in its own window — everything from earlier is already marked processed and skipped, so the reminder fires about ~nothing exactly when a backlog exists. (email-gmail-triage: the 9pm "unread Action emails" reminder was fed the 21:00 run's freshly-triaged set; an Action email from 2pm was already in `processed_ids`, so the reminder almost never fired.) Fix: build the reminder from a fresh query of the **actual outstanding state** (`label:Hermes/Action is:unread`), never the per-run batch list. Tell: a "remind about all outstanding X" feature whose input is a variable populated only inside the current run's loop.
- **Non-atomic state write + unguarded read = one crash bricks every future run.** `open(STATE_FILE, "w")` truncates the live file at `open()` time — *before* any `flock` (and `flock` is advisory, so a concurrent reader sees the empty file anyway). A crash mid-`json.dump` (power loss, OOM kill — routine on a Pi) leaves empty/partial state, and an **unguarded** `json.load` in the reader then raises **every** subsequent run, so the skill is dead until a human intervenes — not a one-off traceback but a permanent stall. Fix: write atomically (serialize to a temp file in the same dir → `flush` + `os.fsync` → `os.replace`, which is atomic on POSIX so a reader always sees a complete old-or-new file), **and** guard the read (`try/except (JSONDecodeError, ValueError)` → log loudly, start from empty so the next write self-heals). (email-gmail-triage. Extends *unguarded file load* with the write-side root cause + the permanent-abort failure mode.)
- **A destructive follow-on action that runs even when the prior step silently failed — and removes the item from its own retry path.** A helper swallows its failure (warns + returns) and the caller then performs an irreversible action unconditionally; worse, that action takes the item *out of the set the next run scans*, so it can never be retried. (email-gmail-triage: `apply_labels` caught its API error, warned, and returned; `main` then unconditionally `mark_read` + `archive`d the Auto-filed email — so a transient label failure filed it out of the inbox with **no** `Hermes/` label: invisible, and no longer `in:inbox` so never re-discovered.) Fix: have the helper **return success/failure**, gate the destructive step on it, and on failure leave the item untouched **and unrecorded** so the next run re-finds and retries it. (Sharpens *swallowed subprocess failure* + *premature cleanup*: the new twist is the failure erasing its own retry path.)
- **A latent crash that the skill's own documentation arms.** A bug that never fires only because the triggering state never occurs in practice — but the skill's *own* docs instruct the user into exactly that state. (spotify-playlist-refresh: `_pick_discoveries` did `{t["track_id"] for t in blocked}` where `blocked` is a set of id **strings** → `TypeError: string indices must be integers`; it never fired because the blocklist was always empty — yet the troubleshooting doc told users the remedy for an unwanted track was to **manually `INSERT INTO blocklist`**, which would crash the very next refresh. The sibling `_pick_wildcards` iterated the same set correctly, proving the inconsistency.) Fix the bug; and when tempted to downgrade a "latent, never observed" finding, **grep the skill's own docs for instructions that would create the triggering state** before lowering severity.
- **A config block that's dead because the code hardcodes its values.** A `config.yaml`/settings file advertises tunable parameters the code never reads — editing them does nothing, and worse they *drift* from the real hardcoded constants, so the config becomes a doc that lies. (spotify-playlist-refresh: `config.yaml` declared `scoring.window_days: 30` / `half_life_days: 14` and a whole `playlist:` block while `scorer.py`/`composer.py` hardcoded 7/7 and the 12/6/2 counts — none of it was loaded.) Fix: grep that **every** config key is actually read by some module; wire the live ones (defaults = current values, to preserve behavior) and delete or clearly mark the rest. (A config-side instance of *doc↔code drift*.)
- **A "self-correction" / backfill that is a no-op or corrects the wrong target.** A routine meant to repair a previously-stored approximate value instead recomputes an already-correct value, or targets the wrong row, or is silently blocked by the write mode. (spotify-playlist-refresh: `_update_last_event_self_correct` recomputed `events[-2]` of the *current* batch — already correct from `_infer_ms_played` — instead of the *previous poll's* optimistically-stored last event; and even targeting the right row, `INSERT OR IGNORE` would have dropped the corrected value. Net: the documented cross-run correction never happened, biasing scores upward; ~56% of in-window rows sat at the optimistic `ms_played == duration_ms`.) Fix: prove the corrective write actually changes the intended row on live data (before/after value) and that the upsert/conflict mode permits the update — a backfill you can't observe changing anything is dead code.
- **The empty/zero path returns a different shape than the happy path.** A function returning a rich shape on data but a bare/smaller one when empty breaks every caller's unpacking exactly when input dries up. (spotify-playlist-refresh: `compute_affinity` returned `({}, now_ms)` normally but a bare `{}` on an empty scoring window → callers doing `scores, ts = …` hit `ValueError: not enough values to unpack` after any listening gap; reproduced by forcing an empty window.) Fix: return the same shape on every path; test the empty/zero case explicitly.
- **A `no_agent` script whose real work exceeds the scheduler's *global* script-timeout watchdog.** The cron scheduler runs each `no_agent` script under `subprocess.run(timeout=_get_script_timeout())` and **SIGKILLs** it on expiry — a single global cap (resolution order: module-patch `_SCRIPT_TIMEOUT` → env `HERMES_CRON_SCRIPT_TIMEOUT` → config `cron.script_timeout_seconds` → **120 s default**); **there is no per-job timeout** (`hermes cron edit` has no `--timeout`, `jobs.json` has no timeout field). A job whose legitimate runtime grows past 120 s (a backup that zips a 444 MB DB + uploads ~360 MB) is killed mid-run **every time**, and a SIGKILL can't self-notify → silent weekly failure. The tell: `last_error: "Script timed out after 120s"` on a job whose work is genuinely long and growing. Fix: raise the **global** knob (config/env) with headroom (measure the real pipeline first — see performance.md), and bound each internal step below it so a slow step fails *with* a notify before the SIGKILL. Note the blast radius: the raised watchdog applies to **all** `no_agent` jobs. (hermes-backup, job 999de4b21eec.)
- **A doc/runbook prescribes the fix, but the config was never actually changed — "documented" ≠ "applied."** A config-side cousin of *implementation-contradicts-its-own-SKILL.md*: the skill's own `backup-debugging.md` *and* `SKILL.md` said in bold "increase the cron timeout to 600 s … it runs 177–220 s," yet `config.yaml` still had the 120 s default and the job died weekly. A confident "we set X" in the docs is a claim to **verify against the live config**, not to trust. Fix: grep the actual config/env for every value a doc says is set, and reconcile; treat a doc-stated setting with no matching live value as a bug. (hermes-backup.)
- **A killed parent leaves an orphaned grandchild that finishes the job after it's marked failed.** `subprocess.run(timeout=N)` in the scheduler kills only its **direct** child (the script PID), not the process *group* (no `start_new_session`/`killpg`). A grandchild the script spawned (`hermes backup`) keeps running after the SIGKILL and finishes writing its artifact seconds later — so you get a **valid-but-unprocessed** file on disk (a "ghost" zip whose mtime is *after* `last_run_at`) while the job shows `error`, plus a leaked process doing heavy I/O the scheduler thinks is gone. The tell: an output artifact newer than the recorded failure time. (hermes-backup: the timed-out backup zip's mtime was 3 s past the kill.)
- **A `no_agent` job with `deliver: local` whose only user-facing alert is the script's *last* step.** `deliver: local` means the scheduler saves output to disk and **does not push** a failure alert anywhere — so if the script's Discord notify is the final step, *any* early exit/kill (timeout, `sys.exit(1)`, crash) pings **nobody**; the failure is invisible until a human looks at cron status. Fix: route **every** hard-failure path through a `fail()` that notifies *then* exits non-zero (don't rely on a happy-path notifier at the end), since the scheduler won't do it for a local-deliver job. (hermes-backup; confirmed by the live failure that sent no alert.)
- **Stale state re-activation: staleness check exists in READ path but not WRITE path.** A cache/store with a staleness check on read (e.g. "if age > 7 days, return empty") can still have its stale data re-activated by the write path, which loads the stale entries without an age check, appends new data, and saves with a fresh timestamp. The next read sees a "fresh" cache that contains old entries. (food-recommender: `get_recent_recommendations()` correctly returned `[]` when the cache was >7 days old, but `save_recommendation_cache()` loaded the stale entries, appended new ones, and saved with today's date — re-activating restaurants that should have been evicted.) Fix: check staleness in the WRITE path too — if the cache is stale, reset it to empty before appending new entries, rather than extending the stale list. Tell: a staleness guard in only one direction (read OR write, not both) always has a漏 path.
- **A full off-box backup ships live credentials in the clear.** A "back up everything and upload to cloud" job archives `~/.hermes` wholesale — including `google_token.json` (a refreshable OAuth token for Drive/Gmail/Calendar), `.env` (bot tokens), `auth.json`, `profiles/*/.env` — so the uploaded artifact is a durable credential-exfiltration surface for anyone with read access to the destination folder. This is a **policy** call, not a silent "fix": surface it and let the user choose (leave as-is for one-step restore / scrub secrets / **encrypt before upload**). If encrypting, gpg symmetric AES256 works non-interactively under cron (`--batch --pinentry-mode loopback --passphrase-file`), but the passphrase must live **off** the Pi (it's inside the encrypted backup, so a Pi-loss with no off-box copy makes the backups unrecoverable). Encrypt only the off-box copy; a local plaintext copy adds no exposure the Pi doesn't already have. (hermes-backup.)

- **A sentinel/default value receiving a systematic scoring bonus.** A scoring system that gives "variety" or "diversity" points for being *different* from the user's history can inadvertently give the highest bonus to a catch-all/sentinel category ("General", "Other", "Unknown") that is never in the user's top-N — because it's a label for *unclassifiable* items, not a real category. The sentinel gets +10 every time while real favorite cuisines get 0 (variety=0 + affinity=5 - recency=5). (food-recommender: "General" cuisine restaurants systematically outscored well-matched restaurants in the user's favorite cuisine.) Fix: exempt the sentinel from variety/affinity/recency bonuses, or require the category to appear in a reference list before it's eligible for scoring. Tell: a "catch-all" category that always gets top score in a diversity bonus system.
- **A display name used as a unique dedup key when names aren't unique.** Deduplicating by `r["name"]` treats every "McDonald's" or "Starbucks" as the same entry — but chain restaurants have multiple physical locations at different distances, and the user may want the closer one. Only the first occurrence survives; subsequent locations are silently dropped. (food-recommender: `fill_top_n` dedup by name dropped 2nd/3rd locations of chains, which are very common in Singapore.) Fix: deduplicate by `(name, lat, lon)` tuple or by `place_id` — treat different coordinates as distinct entries even when names match. Tell: any entity where the display name is not a natural key (chains, franchises, common names).
- **Asymmetric guarding of a paired field — and a filter-site guard that doesn't cover the format site.** Two fields always used together (`latitude`/`longitude`, `start`/`end`, `width`/`height`) but guarded *asymmetrically* — every check tests `latitude is not None` and silently omits `longitude` — so a record with one half null sails through and crashes (or formats wrong) at the first site that touches the *unguarded* half. Worse, a `is not None` guard added to the *filter* functions does **not** protect a *later* loop that re-dereferences/formats the same field (`f"{c['latitude']:.6f}"` in a summary/table/URL builder); and a *truthy* guard there (`if c["latitude"]`) is its own bug, since a legitimate `0.0` is falsy → prints `"?"`. Fix: guard **both** members of a paired field at **every** dereference (filter *and* format/label sites), with `is not None`, never truthiness, for numeric fields that can be `0`. (backup-cleaner: `validating_run` accepted an `ok` from a disabled job — `food_recommender.py`, `enabled:false`, last ok weeks earlier — as proof a backup's update was validated; fixed by skipping `enabled is False` jobs in the index.) Tell: an evidence query over a jobs/feeds table filtering on `status=="ok"` but not on `enabled`/`active`.
- **A hardcoded absolute base path is a testability blocker AND a latent coupling — make location roots env-overridable so the shipped regression suite can drive them.** A skill that classifies/resolves *by filesystem location* (a skills root, a scripts dir, a vault path) often hardcodes `~/.hermes/…`; a `/tmp` fixture then can't exercise the location-dependent branch, so the very logic that most needs a test is untestable — and the code silently assumes one deployment layout. Make each base dir `os.environ.get("X_DIR") or <default>` (same pattern as a manifest/log-path override), so the shipped suite points them at a fixture. (backup-cleaner hit this **twice** — `owning_skill` hardcoded the skills root, then a fix hardcoded the scripts root; both broke the fixture until made env-overridable, at which point the safety-critical classification cases became regression-testable.) Tell: a hardcoded `~/.hermes/<root>` inside a classifier/resolver whose fixture test can't reach the branch using it. (Pairs with the safe-edit rule *ship a regression suite* — a location-classifier isn't really testable until its roots are injectable.)


- **A health/validation check that shells out to a CLI not on the *non-login* PATH reports a false failure in exactly the environment it runs in.** A skill runs its scripts via the agent terminal tool and the cron scheduler — both **non-login shells** whose PATH is `/usr/local/bin:/usr/bin:/bin` and does **not** include `~/.local/bin`. A `subprocess.run(["hermes", ...])` (or any user-installed CLI) therefore hits `FileNotFoundError` there, and a check that infers state from that call reports the resource *absent*. (cc-bill-review: `verify_cron_health()` shelled out to `hermes cron list`; the missing binary made it report the reminder cron "not found", so `reminder_confirmation()` cried "🚨 Payment reminders may NOT fire" after **every** statement import — while the cron was healthy and firing daily.) Fix: read the **structured source of truth directly** (here `~/.hermes/cron/jobs.json` — the scheduler's own state file — no PATH/CLI-format dependency), and resolve the binary by **absolute path** (`~/.local/bin/hermes`, `shutil.which`) only for *mutating* actions that genuinely need the CLI. Tell: a `subprocess.run(["<bare-cmd>", ...])` whose result feeds a user-visible "is X healthy?" claim; reproduce it by running the check in a non-login shell (`env -i`, or just a fresh `ssh host 'command -v <cmd>'` → exit 1). (Sibling of *rate-limit-mimics-empty* / *not-found-conflated-with-error*: an unreachable **checker** reads as a failed **subject**.)
- **A health check that conflates "couldn't determine the state" with "the state is bad" false-alarms whenever its evidence source is unavailable.** The mirror of the class above at the *logic* level: even after you make the check robust, if "no data" collapses into "unhealthy", any transient unavailability of the source pages the user. Fix: return a three-valued result — **healthy / unhealthy / undeterminable** — and have the human-facing layer emit a hard alarm **only** for a *confirmed*-bad state; for undeterminable, degrade to a soft note ("couldn't verify from here; the daily job runs independently"). (cc-bill-review: `verify_cron_health` grew a `determinable` flag; `reminder_confirmation` shows 🚨 only when the job is confirmed absent/paused, a soft ✅-note when jobs.json + CLI are both unreadable.)
- **A skill that runs under TWO interpreters must be validated under BOTH — and a top-level heavy import couples an unrelated path to a dep it never uses.** An *interactive* skill script run by the agent uses the **system `python3`** (user-site enabled → `~/.local` packages like `pymupdf` present), while its **`no_agent` cron** path runs under the **gateway venv** (`~/.hermes/hermes-agent/venv/bin/python`, user-site *disabled*). The same file can import fine in one and `ModuleNotFoundError` in the other. Compounding it: a module-top `import <heavy>` makes *every* importer pay for it — so the delivery-critical reminder path (which only needs the DB helpers) dragged in `pymupdf`, and a broken/missing wheel under the venv would kill the reminder **silently at import** on a `deliver: local` job. Fix: validate/`py_compile`+dry-run under **both** interpreters (sharpens safe-edit's "compile with the interpreter that runs it"), and make a heavy dep a **lazy import** inside the one function that uses it so unrelated paths don't depend on it. (cc-bill-review: `reminder.py` → `parse_ocbc` top-level `import pymupdf`; moved into `read_pdf_text`; confirmed `import scripts.reminder` then needs no pymupdf. The wrapper's PEP-668 user-site shim is the *other* half of this — needed because the venv strips user-site.)
- **A normalizer that strips tokens matching a broad set silently deletes legitimate tokens that happen to be in that set — surface it by re-deriving every stored value from its raw input and diffing.** Expanding a strip-set to be "complete" (here `COUNTRY_CODES` from ~40 to the full ISO alpha-2 list, to stop dropping unknown countries) can start eating real name tokens that are *also* codes: "MP" (a Shopee **m**arket**p**lace tag → MP = Northern Mariana), the leading "LA" of "LA BOTTEGA DEL TART" (→ Laos). The item fragments into a new normalized key on the next import → a false "🆕 new merchant" (the exact thing the skill exists to prevent) and the canonical-map key no longer matches. **The high-value probe:** re-run the current normalizer over **every distinct raw value in the live DB** and diff against the **stored** normalized column — non-zero drift is either a latent bug (stored is right, code now differs) or proof your fix is behaviour-preserving (drift must return to 0). (cc-bill-review: the drift check found exactly the MP/LA rows; the fix — a `{MP, LA}` keep-list — was accepted only once drift went back to **0/130**.) Tell: any `if tok in BIG_SET: drop` over free-text tokens where a member of BIG_SET could be a real word.
- **Fixing an over-broad strip can silently REGRESS lookups that were riding on it.** The over-strip above was *also* load-bearing by accident: stripping "BY" (Belarus) turned "GOMO **BY** SINGTEL" into the canonical-map key "GOMO SINGTEL", and stripping "LT" (Lithuania) turned "JUNGSUNGHAIR PTE **LT**" into its key — a naive "just strip trailing country codes" fix broke both, re-fragmenting merchants that had been canonicalizing correctly. (A normalizer+lookup-table instance of *provider-fallback rides on the primary's failure mode / fixing the primary demotes quality*.) Fix: make the change **minimal and drift-verified** (exempt only the specific offending tokens) rather than "principled but broad"; prove drift=0 over the whole live corpus before shipping, because the map keys are tuned to the *current* normalization.
- **A `no_agent` wrapper that sends N independent messages then records "sent" for all of them AFTER the loop re-delivers the successful ones when a later send fails.** Sharpens delivery-reliability's *record-state-after-all-sends* for the case of **independent** items (here one reminder per card, and both cards routinely share a due date): marking *all* items fired after the loop means a 2nd-card 429/5xx aborts before the mark, so the already-delivered 1st card re-sends next run — a duplicate. Fix: mark **each item immediately after its own successful send** (per-item, inside the loop), wrap each send in try/except, and leave a failed item unmarked so only *it* retries. (cc-bill-review `cc_payment_reminder.py`; reproduced by monkeypatching `urlopen` so send #1 succeeds and #2 raises → only card #1 marked.) The all-or-nothing rule is for a *single logical unit*; independent sends need per-item bookkeeping.

- **An unguarded per-row parse (`date.fromisoformat`, `int(...)`) lets ONE malformed row crash the whole report — and takes down a *secondary* consumer that depends on the same output.** A read-only reporter that parses a per-item field with no try/except aborts the entire run on a single bad value, and if another tool consumes its `--json`/dump to resolve something (task-tracker's agent runs `--json` to map a table row-number → task id for "done N"), that consumer dies too. The malformed value is **realistically produced by the write path**, not just corruption: an LLM/natural-language date writer ("May 15" → current year) can emit a **non-zero-padded** date like `"2026-7-6"`, which `date.fromisoformat` rejects as invalid ISO on Python 3.11+ (verified on the Pi). And **key-presence validation does not catch a bad *format***: a write-path "validate each task has id/name/category/last_done" step passes a task whose `last_done` is present-but-unparseable. Fix: guard the parse per-row; keep the bad row **visible** (show the raw value + a "Bad date" status) rather than dropping it — dropping shifts the running counter the secondary consumer relies on. Also add a format check to the *write* path (require zero-padded ISO or `null`) so the bad value never lands. Tell: a `fromisoformat`/`int()`/`strptime` on a per-item field inside a loop that builds a whole report, with the only error handling at the file-load layer. (task-tracker `build_sections`; one bad date blanked all 31 tasks + the `--json` resolver, in every mode.)
- **A `try/except` scoped to the *parse* but not to the *arithmetic that consumes the parsed value* leaves a second crash site — and the terminal-gate refuter caught it as a regression in the fix's own claim.** Having wrapped `date.fromisoformat(ld)` to stop a bad date crashing the report, the fix still did `next_due = ld + timedelta(days=interval)` **outside** the guard — so a date that *parses* but sits within `interval` days of `date.max` (year 9999) overflowed with an uncaught `OverflowError`, defeating the very "one row can't crash the report" promise the fix advertised. The non-adversarial regression-lens reviewer confirmed byte-identical good-data output and missed it; only the **adversarial refuter's year-9999 probe** surfaced it. Fix: guard the *whole use* of a parsed value (parse **and** the computations that consume it), not just the parse call; when the downstream op can throw on extreme-but-parseable input, catch it and degrade to the same "bad" presentation. (task-tracker `build_sections`; reproduced `"9999-12-31"`/`"9999-12-25"` → OverflowError, then reclassified overflow → "Bad date".) A guard-placement cousin of *`except` narrower than the failures that occur* — here the guard is narrower than the *value's lifetime*, not the exception set. Reinforces **run the fan-out on your own applied fixes** and **the adversarial refuter earns its keep at the gate** (the plain regression lens won't probe absurd inputs; the refuter must).

- **A hardcoded label/index list applied to a TIME-RELATIVE API window ships correct-looking output in the window you happen to test and WRONG output at the scheduled run time.** An API array whose element ordering depends on the *request time* — NEA's 24hr forecast returns 3 periods anchored to the 06:00/12:00/18:00 boundaries with `period[0]` = the *current* block, so the set slides with the clock — fed to a fixed label list (`["Midday–6pm","6pm–6am (tonight)","6am–Midday tomorrow"]`) mislabels every run except the one time-of-day the list was written for. The killer: the labels *happened* to line up in the evening (where a maintainer eyeballed them and even wrote a doc "correction" blessing them) but the job runs at **07:25**, where the periods are `[6am–Midday, Midday–6pm, 6pm–6am]` — so all three lines were shifted forward one slot **every single morning**, silently misinforming the reader ("tonight" was actually this afternoon). Fix: derive each label from the datum's OWN metadata (`period["timePeriod"]["text"]`/`.start`/`.end`), never from position. **Two method points this sharpened:** (a) *validate a scheduled skill's output at its REAL trigger time, not a convenient one* — a fresh off-schedule run looked perfect while the 07:25 cron was wrong; the proof was in the **archived cron-output docs** (`~/.hermes/cron/output/<job>/`) from actual 07:25 runs. (b) *look for an internal-consistency TELL rather than trusting the labels* — three archived outputs printed `6am–Midday tomorrow: Partly Cloudy (Night)`, and a **`(Night)` weather code cannot describe a 06:00–12:00 daytime block**, which pinned the mislabel objectively without waiting for a 07:25 run. Tell: a fixed label/index list over an API array (forecast periods, "next N hours", tide/market windows) whose ordering or contents are relative to *now*. (sg-commute `morning_commute.py` `section1`, 2026-07-12.)
- **A fix that starts consuming a NEW input field inherits that field's failure modes — a shape-migration in that field can crash a path the old code never touched.** When a fix reads a field the replaced code ignored, it takes on every way that field can be malformed (a `null`, a future `{code,text}` dict-migration — the exact thing that already happened to sibling fields `regions.<region>` and `general.forecast` in the same API). The period-label fix above read `timePeriod.text` **outside** `section1`'s inner per-period `try/except`, so a non-string `text` would `TypeError` in `re.sub` and collapse the *entire* Weather section (losing the temp/humidity/wind header too) — a blast-radius **regression the terminal gate caught in the author's own fix** (both gate reviewers flagged it independently). Fix: guard a newly-read field at least as tightly as the code it replaces (put the read inside the existing per-item guard) and normalize it through the skill's *existing* dict-or-string helper (`_fc_text`) rather than assuming today's string shape. Tell: a fix that reaches into a new sub-field of an API object whose *sibling* fields have already been observed to change shape. (sg-commute `_period_label`, 2026-07-12. A new-field cousin of *`.get(key,default)` returns the default only when the key is ABSENT* + *guard the whole use of a parsed value*.)

- **A rolling `now − Nh` window GROUPED BY calendar day yields a variable partial-day bucket count that shifts with the run's clock — anchor the lower bound to a calendar boundary if you mean "N *calendar* days."** A report bounded `WHERE ts >= (now − timedelta(weeks=1))` (a 168h *instant*) but grouped by `strftime('%Y-%m-%d', ts, '+8 hours')` spans **8** partial SGT calendar-day buckets whenever the cron fires mid-day (day−7's afternoon slice + days −6…0), and silently omits any day with zero rows — so a table titled "Last 7 Days" renders 6–8 rows depending on the hour it ran *and* the data. It looks right whenever you eyeball it off-schedule and is wrong by a partial row at the scheduled time — the scheduled-skill tell again (validate at the REAL trigger time). Fix: anchor the lower bound to the calendar boundary — `today = now.replace(hour=0,…); bound = today − timedelta(days=N−1)` — for exactly N whole calendar days (`.replace()` preserves tzinfo; a fixed-offset tz like SGT has no DST, so the arithmetic is unambiguous across month/year rollover). Tell: a `timedelta(hours=…|weeks=…)`-relative lower bound feeding a query that `GROUP BY`s a *calendar* truncation of the same column. This is a behavioral/framing call — surface "rolling N×24h vs N whole calendar days" to the user, don't silently retune. (token-usage 1.1.0: the weekly "Last 7 Days" table; user chose 7 whole SGT days.) **The other half of this class: a `GROUP BY` over the calendar window drops zero-activity buckets entirely** — if the report should be a fixed-height N-row table, zero-fill from a Python date spine (`[(today − timedelta(days=i)).strftime(k) for i in range(N−1,-1,-1)]`, then merge query rows by day-key, emitting an explicit `0`/`$0.0000` row for a missing day), else a quiet day silently shortens the table. This is a *foreseeable follow-up* the moment you anchor a windowed report — surface it *with* the window change, don't ship the anchor and wait for the user to notice a vanished day. (token-usage 1.1.1 — the very next request after 1.1.0: Jul 8 had 0 sessions and dropped out of the 7-day table.)
- **A skill that CONSOLIDATED to one script can leave orphaned same-stem siblings in `~/.hermes/scripts/` that no cron runs but that still carry the old anti-patterns.** When a multi-script pipeline (`X.py` + `X_dispatch.py` + `X_debug.py`) is superseded by a single consolidated `X_no_agent.py`, the earlier-generation files often survive in the shared scripts dir — unreferenced by any cron, but still `MEDIA:`-tagging / reading the token from `os.environ`, and still auditor-flagged. They are footguns (a curator could wire one to a cron) and audit noise. Fix during Phase 0 / the bug hunt: after resolving the live copy, list same-stem siblings (`ls ~/.hermes/scripts/<stem>*.py`) and cross-check each against `jobs.json`; an orphan referenced by **no** job is dead — report it (and, if in-scope, remove with a backup). Tell: several `~/.hermes/scripts/<stem>*.py` where the cron's `script` names only one. (token-usage: `token_report.py` / `token_report_dispatch.py` / `token_report_debug.py` lingered from the May pipeline after the June consolidation to `token_report_no_agent.py` — surfaced by pointing the auditor's `--scripts` at the shared dir.) (A shared-dir cousin of Phase-0 *copy↔copy drift* and the backup-cleaner orphan classes.)

- **A timeout/hang fix that bounds only the ONE call that crashed is INCOMPLETE — and `retry()` wrapped around an *unbounded* per-attempt call can itself blow the cron watchdog.** When you're asked to "assess yesterday's timeout fix," check it for **completeness across all sibling blocking calls**, not just whether it stops the observed crash. Two traps: (a) wrapping the crashing call in `retry()` while leaving its siblings unbounded — a `subprocess.run` with **no `timeout=`**, or a `googleapiclient` service built with no HTTP timeout — so a hang *elsewhere* still runs to the ~120s SIGKILL (uncatchable → no alert on a `deliver: local` job); and (b) `retry()` around a call whose single attempt can take ~minutes means `attempts × per-attempt-timeout + backoff` can *exceed* the watchdog, turning a fast catchable failure into a silent kill — a "fix" that makes it worse. The complete fix bounds **every** boundary and caps cumulative retry time: `subprocess.run(timeout=T)`; `socket.setdefaulttimeout(T)` to bound in-process `googleapiclient`/`httplib2` calls that `build()` won't easily accept a timeout for (the clean lever); and a **run-global monotonic deadline** consulted in `retry()` **pre-start** (don't begin a new call past it) *and* **pre-sleep** (don't back off across it), so the worst case is one in-flight call (≤T) after the deadline. Keep the invariant `RUN_DEADLINE + T + crash-alert-budget < watchdog`. Tell: an auditor `subprocess-call-with-no-timeout` MED next to a recent "wrapped X in retry() to fix a timeout" change. (foodpanda 2026-07-18: the 07-17 fix wrapped only `get_all_sheets().execute()`; `run_gapi`'s subprocess and every other `.execute()` stayed unbounded — completed with `socket.setdefaulttimeout(20)` + `subprocess timeout=20` + a `_run_deadline` gate; the **terminal gate caught a regression in the tuner's own first cut** — the deadline was checked only *between* attempts, so an in-flight call + the crash-alert retry storm still breached 120s, fixed by the pre-start/pre-sleep gates + a single-shot crash alert.)
- **MEASURE a call's real cold latency before you pick its timeout — a timeout guessed from an assumption false-trips a legitimately-slow call, and a `no_agent` cron exposes it unattended on the very next run.** When you add a `timeout=` (the fix above), the *value* is a correctness decision, not a formality: set it below the call's genuine worst-case and you convert "occasionally slow" into "fails every slightly-slow run." Profile the exact call **cold** (fresh process, real network/auth — not warm, not in-process) before committing a number, and leave generous headroom under the watchdog invariant. Watch especially for a call that looks cheap but isn't: a `run_gapi`-style **subprocess** pays cold-interpreter + OAuth on every invocation, and a "search" that **hydrates N results** (per-message metadata) scales with N, not with "it's just a search." The deeper fix is often to shrink the work (narrow the query window to the incremental watermark so it returns a handful, not the full `--max` cap) so the call is fast *and* the timeout is comfortable. Neither offline import-tests nor the gate's timing *math* catch this — only timing the real cold call does. (foodpanda 2026-07-19: `CALL_TIMEOUT=20` from the 07-18 tune-up killed the cold `gmail search` subprocess — measured **16–25s** because it hydrated the full `--max 50` of historical receipts — on the first scheduled run after the tune-up; fixed by narrowing the search to `after:<watermark−1d>` (~2s) and raising the timeout to 30. The hardening *worked* — it failed cleanly with an alert instead of a silent SIGKILL — but the guessed value made a clean failure a nightly one.)
- **The "report once" alert re-fires not only when its timestamp is excluded from the watermark, but when a deterministic skip sits NEWER than a still-*retryable* fetch failure that pins the watermark below it.** Sharpens the incremental-cursor class above: the earlier foodpanda fix put the skip's timestamp *into* `processed_ts`, but the watermark is still bounded **strictly below the earliest retryable (fetch) failure** — so a parse/foreign skip newer than that failure can never advance past it, and its once-only alert re-fires **every run** until the transient fetch clears (potentially forever, for a permanently-unfetchable item). A scalar watermark cannot express "handled this, still retrying that older one." Fix: dedup the alert on a **persisted set of already-reported ids**, saved **independently of the watermark AND of the `any_failure` guard** (an early `save_state` of just the reported-ids, so it sticks even if the run later aborts), bounded to the last N. (foodpanda 2026-07-18: a `⚠️ Unparseable` / `ℹ️ Non-SGD` alert re-fired whenever a skip's `email_ts` sat above a same-provider fetch failure; fixed with `reported_skip_ids` in state. All three blind reviewers flagged it independently.)

## Fan out independent reviewers (REQUIRED — not optional)
**Every bug hunt must do this — never audit solo.** **This protocol runs twice in a tune-up:** (a) *during* the bug hunt to **find** bugs in the original code (below), and (b) again as the **terminal validation gate** over the *cumulative* diff of **all** passes before you declare done — and that second run is mandatory for *every* engagement that changed code (perf-only / token-only / delivery-only included), because your own late edits (a perf refactor, a delivery rewrite) are the least-reviewed code in the repo. See `SKILL.md` → *Terminal validation gate*. Spawn **N independent *blind* reviewers** — each sees the code + live data but **not** each other's findings (and not yours) — then triage by **agreement count** (e.g. fix every bug ≥2 of N flag). Independence raises recall (each surfaces what the others miss) *and* filters false positives (a blind reviewer refutes an over-eager claim). Caveat: point every reviewer at the **live** copy (Phase 0 / Step 0), or they'll agree loudly about bugs in dead code.
- **Run the fan-out on your *own* applied fixes too, not just the original code.** Your edits are the least-reviewed code in the repo — after fixing, point a reviewer (or a dedicated adversarial-refuter pass) at the post-edit diff to hunt regressions you introduced. (spotify-playlist-refresh: the author's atomic-`auth.json`-write fix fell back to `{}` on a read error and would have rewritten a provider-only file, **wiping other providers' credentials** — a regression no solo pass caught; an independent refuter flagged it and it was fixed before shipping. The single most valuable thing the fan-out did that tune-up was review the author's own work.)
- **Give the reviewers different lenses, not identical copies.** Blind-but-redundant reviewers tend to converge on the same findings; assigning each a distinct angle — control-flow/state, edge-cases/data-shape, and one **adversarial refuter** told to *disprove* each candidate (default "not a bug") — raises recall *and* hardens the false-positive filter.
- **The refuter's highest-value target is the solo reviewer's TOP finding.** Confirmation bias is strongest on the "obvious" bug — the one the reviewer classified highest. In food-recommender, the solo reviewer classified "cache FIFO doesn't evict by age" as HIGH; the refuter convincingly showed it was a false positive (the 50-entry cap evicts in ~5 days, faster than the documented 7-day window). The *real* bug (stale entry leak on save) was a subtler finding from a different reviewer. If the refuter only challenges minor findings, the solo reviewer's most confident mistake ships unchallenged.
- **Resolve a disagreement with a cheap targeted probe, not a majority vote — and don't trust a reviewer's own "I verified it."** When reviewers split on a finding, reproduce the *exact* code path in the real runtime and let the result decide. (foodpanda: one reviewer "verified" a locale-dependent `strptime` bug, but the script never calls `setlocale`, so the live Pi interpreter parsed the English date fine — a 30-second probe disproved it; a separate missing-tab claim was *confirmed* the same way. Both beat arguing from the source.)
- **A stale/wrong reference DOC can make your blind reviewers REFUTE a real, live-confirmed bug — when a reviewer cites a doc (especially one that says "verified") to kill a finding, re-verify the DOC against live data, don't accept the citation.** Blind reviewers read the skill's own `references/` as ground truth; a confidently-wrong doc note therefore doesn't just mislead a human, it manufactures *agreement* against a true finding. (sg-commute 2026-07-12: `weather-api-response-shapes.md` carried a dated "Correction … verified against the live cron output" blessing the hardcoded period labels; **two independent blind reviewers cited it to refute the period-shift bug** — but the doc's author had only eyeballed the labels, never checked the periods' Day/Night codes, so "verified" was false. Three archived 07:25 cron outputs with a `(Night)` code under a daytime label overturned both reviewers *and* the doc.) This is the doc-side of *don't trust a reviewer's own "I verified it"* and a live instance of *documented ≠ applied/verified*: treat a reviewer's doc-citation as a pointer to *re-run the probe*, and if the doc is wrong, fixing the doc (dated correction) is part of the fix — leaving it re-arms the same false refutation next tune-up. Tell: a reviewer refutes a finding you confirmed on live data, and the refutation traces back to a doc claim rather than to the reviewer's own reproduction.
- **For an *encoding* dispute the probe is a literal round-trip — and "everything is escaped" is usually correct, not a bug.** (google-route-map: a reviewer confidently flagged the URL builder's full percent-encoding — `quote(safe='')` turning `|`→`%7C`, `:`→`%3A` over the whole `path` value — as "corrupting the polyline so no route draws"; a 3-line `quote`→`unquote` round-trip showed it decodes back byte-identical, and full-encoding is in fact **required** because the encoded-polyline alphabet itself contains `|` and `\`. The other two reviewers had it right; the probe, not the 2-vs-1 count, settled it.)
- **Agree on a fix-threshold up front — severity × agreement-count — so you neither fix everything nor argue each one.** With multiple reviewers (+ your own pass) you get more candidates than are worth touching; pick a bar before triaging (e.g. *act on ≥ Medium severity AND flagged by ≥2 reviewers*) and let the user set it if it's their call. Findings below the bar still get reported, not silently dropped. (email-gmail-triage: 8 candidates → 4 fixed under that bar in one round; the rest were logged for the user to opt into, two of which they then asked for.)
- **A self-introduced false-positive is a DEFECT to fix even when the refuter shows "0 rows hit today" — that's different from a genuine behavioral-breadth call.** When the data-shape reviewer rates an over-match HIGH and the adversarial refuter answers "theoretical — 0 of the current N rows are affected," don't let the refuter's *live-data* framing downgrade it to a no-op: if the over-match is in code **you** shipped a session or two ago (a filter/guard you widened), it's a regression you introduced, the corpus only grows, and the collision is a real naming pattern elsewhere — so fix it. Reserve the "surface options, don't silently retune; behavioral/ranking params are the user's call" rule (see the doc↔code bug-class) for a genuine *preference* (how aggressive should exclusion be, what counts as a favorite), not for an accidental over-broad match that drops legitimate items. The tell: "the fix un-blocks real studio titles and blocks nothing new" — that's a bug fix, not a retune. (spotify-playlist-refresh 2.13.1: the live filter's delimiter-free `Live in/on …` branch wrongly caught studio titles like "Live in the Moment"/"We Live On"; the refuter correctly found 0 of 156 real tracks hit it *today*, but it was a self-shipped over-match, so dropping `in`/`on` from that branch — while the paren/dash branches still catch `(Live in X)` — shipped as a fix, verified by 0 decision-flips across all 156 real names.)
- **A confident *security / spoofing / injection* claim is usually falsifiable (or confirmable) by a literal probe of the actual parser — don't take it on the reviewer's word.** (email-gmail-triage: one reviewer claimed an attacker could "forge VIP status via a crafted display name"; running the real `extract_email` on `"akanestar@hotmail.com <attacker@evil.com>"` returned the *attacker* address (it takes the last `<…>`), so the spoof can't work — disproved in one call. A separate "resolved-Unsure mail goes permanently invisible" claim was killed by reading that triage `continue`s on anything already in `processed_ids`, so it never re-categorizes those at all.) Same discipline as the encoding round-trip: reproduce the exact path, let the result decide.
- **A "review" request IS a bug hunt — don't treat it as lighter.** When the user says "review X skill" or "find bugs in X," that IS the bug hunt engagement. The fan-out is mandatory. Do not read the code solo, present findings, and wait for the user to remind you to fan out. (food-recommender: the solo reviewer classified "cache FIFO" as HIGH severity; the adversarial refuter overturned it as a false positive and the real bug was a subtler stale-entry-leak found by a different reviewer. Without the fan-out, the false positive would have shipped as a fix while the real bug went unaddressed.) The tell: you're about to present findings without having spawned independent reviewers. Stop and fan out first.
- **When the reviewer fan-out is killed mid-run (budget cap / 429 / quota), don't fall back to a solo read — substitute deterministic self-probes per lens.** Reviewer subagents can die partway (e.g. a daily cost-allocation 429), leaving you with fewer perspectives than the protocol requires. Reaching "done" on the survivors alone silently downgrades the gate. Instead, *run the missing lenses yourself as offline, deterministic probes* — which the method already prefers over a vote — and **say in the report exactly which lenses were agent-run vs self-probed**. (sg-car-plate-range: the security and adversarial-refuter agents were budget-killed; the refuter's job — disprove each candidate — was done by a synthetic-HTML unit test that reproduced every parsing finding and validated the proposed parser across 8 cases, and the security lens by a read-only `grep -rn` for the key across the skill dir + git/backup/log exposure. Both are stronger evidence than a model's opinion.) Tell: you're about to write "2 of 4 reviewers agreed" when 2 reviewers never ran — convert their lenses into probes before concluding.

- **Fanning out N reviewers that each SSH/connect to the SAME host can trip its auth throttle (fail2ban) and lock YOU out mid-tune-up.** Independent reviewers are required, but if each one opens many SSH sessions to the target box in parallel, the burst of connections/auth attempts can trip `fail2ban`/`MaxStartups` on the host's sshd — after which *every* connection from your source IP (including the orchestrator's) gets `Permission denied (publickey,password)` even with a valid key, and naive retries **extend** the ban. (cc-bill-review: three parallel reviewers hammering the Pi locked the whole tune-up out of SSH for ~30 min.) Mitigations: point reviewers at a **local snapshot** of the code + a **DB clone** and forbid SSH in their prompt (validate against the copy, not the live box); cap fan-out concurrency; and if you do get locked out, **stop retrying** (each attempt resets the ban window) and wait one fully-quiet interval. Pulling a self-contained review kit (`tar` the skill dir + copy the DB once) up front also makes the reviewers reproducible and offline.
- **A single-fact "green baseline" is fragile when the upstream data can change between runs — and a parser change and a page change look identical in the output.** If your baseline is one fingerprint (yesterday's `SPK`) and today's hardened code emits more (`SPH, SPJ, SPK`), you cannot tell "my new parser over-captures" from "the page genuinely changed" by *running it again*. **Isolate it: fetch the upstream ONCE and run the old and new parser over the *same* body**, plus dump the raw matched elements. (sg-car-plate-range: the LTA page opened prefixes for every vehicle type overnight; the same-body diff proved the new Car-only parser was correct — old would have merged motorcycle/bus prefixes and dropped `XF` — rather than the new code being wrong. A re-run alone would have been ambiguous.) Corollary: capture the baseline as the *raw upstream payload*, not just the final string, so post-change comparisons are apples-to-apples; and beware a live external read that costs money/credits (a Scrapeninja scrape) or has a quota — one tune-up exhausted the API key's quota mid-run, after which all validation had to be offline. Budget your live reads: one baseline + one post-fix confirm, everything else synthetic.

## Report format
For each finding: symptom → root cause (file:line) → fix → severity. Separate **confirmed** (reproduced on data) from **suspected** (code-reading only). Fix the highest-severity, highest-confidence first.

When a fix is **forward-only** (it corrects new data but not rows already written) or it **changes a stored signal/metric**, say so plainly: a quiet system can show **no** live change right after the fix — report that as a no-op (and prove the mechanism deterministically per Method step 4) rather than implying you observed a correction, and note that historical values aren't comparable across the change. (spotify-playlist-refresh: the ms_played fix is forward-only — a poll on a day with no new listening changed nothing live, and affinity numbers shift after it, so old `affinity_snapshot` rows aren't comparable.) This is the inverse of the behavior-preserving fingerprint in performance.md: there you prove behavior *didn't* change; here you flag that it *did*, and how far.

## Bug-classes from the morning-brief tune-up (2026-09-15)

- **One publisher subscribed TWICE breaks both identity and corroboration.** A feed list that
  carries a publisher's main feed *and* its topic sub-feed (The Verge / The Verge AI, Ars
  Technica / Ars Technica AI) delivers the same article under two `source` names. Anything
  keyed on the feed *name* is then wrong in both directions: a seen-ledger hash of
  `title|source` misses the sibling copy (proven from the live ledger — the same title
  recorded under both names 24.01 h apart, i.e. delivered on two consecutive days), and a
  "distinct sources" corroboration count treats one outlet as two and promotes it. Identify an
  article by URL/canonical-title, and an *outlet* by the article link's registrable domain —
  **not** the full host: one feed can span subdomains (Slashdot serves news./games./science./
  yro.slashdot.org), which inflates the count the other way. Clamping the outlet count by the
  distinct feed-name count makes both errors impossible; both bounds only ever under-count,
  and an under-count merely fails to promote.
- **A rank cap that DISCARDS instead of DEMOTING inverts the ranking.** `top = items[:N]` with
  no fallback pool silently drops ranks N+1.. — and if the *next* section is built only from
  items that FAILED the first test, the discarded high scorers never reappear. Live: an
  18.0-score/6-keyword article dropped from the brief entirely while a 12.0/2-keyword one was
  shown. Tell: two selection stages where the second is built from the first's rejects rather
  than from everything that didn't make the cut.
- **A dedup that DROPS an item must also RECORD it.** Where a dedup pass runs after the
  "already seen" filter, the dropped twin is never marked seen while its shown sibling is — so
  the pair cannot re-form next run and the duplicate is promoted and delivered as new. Give
  such records a *shorter* TTL than a genuinely-shown item, so a false dedup pairing costs one
  cycle rather than the full window.
- **A shared ledger's WRITER and READER must apply the identical retention filter.** If the
  writer's "already recorded?" set includes entries the reader considers expired, an item is
  delivered every run and never re-stamped — an unbounded daily-duplicate loop. Test it by
  seeding one entry aged just past its TTL and running reader-then-writer twice: the entry's
  timestamp must refresh.
- **`except (json.JSONDecodeError, IOError)` does NOT catch `UnicodeDecodeError`.** Both are
  `ValueError` subclasses but `JSONDecodeError` is the narrower one, so a truncated write that
  leaves invalid bytes escapes. Use `(ValueError, OSError)` for any "read a JSON file
  defensively" helper. Four helpers in one skill had this hole.
- **Anything between "delivered" and "state written" must be crash-proof.** A raise in that
  window (a prune comparing a malformed `ts`, a `json.dump(allow_nan=False)` on a NaN that
  `json.load` happily accepted, a health-line formatter meeting a non-numeric counter, a
  `resp.json()` on a 2xx with an HTML body) leaves the outward action done and the state
  unrecorded — i.e. the whole report re-sends. Audit that span line by line and coerce every
  externally-sourced value there. A defensive coercion applied on the READ path and not the
  WRITE path is the classic half-applied version.
- **`no_agent` cron discards stderr on SUCCESS.** The scheduler captures both pipes but
  returns only stdout when the exit code is 0, so every diagnostic a pipeline writes to stderr
  is destroyed on exactly the runs you later want to forensically inspect. Tell: `grep -l
  '\[WARN\]\|\[DOWN\]' ~/.hermes/cron/output/<job>/*` returns nothing across dozens of runs
  while the code clearly emits them. Fix in the wrapper: `subprocess.run(..., stderr=
  subprocess.STDOUT)`.
- **A wrapper's own `print()` is block-buffered on the cron pipe.** Children inherit fd 1 and
  flush at their exit, so the parent's "→ step" markers all appear AFTER every child's output
  (useless for attributing a line to a step) and are lost entirely if the watchdog kills the
  run. Fix: `sys.stdout.reconfigure(line_buffering=True)` in the wrapper, and pass
  `PYTHONUNBUFFERED=1` to the children so their own stdout interleaves with their stderr.
- **A "guard against total failure" that tests the wrong quantity.** `if not items: exit(1)`
  passes when a near-total outage leaves ONE unusable item. Gate on the count that the
  downstream actually needs (here: articles passing the paywall guard), not on raw arrivals.

## Extracting a shared helper breaks callers that never initialize its state (2026-09-15)

When a tune-up factors duplicated logic into a shared module, the new module often depends on
module-level state that the *primary* caller arms and a *secondary* caller does not. The
primary path is the one you test; the secondary path is an on-demand tool nobody ran.

Concrete: morning-brief's `feed_doctor.py` (an on-demand utility) reuses
`summarize.call_model` without arming `summarize._DEADLINE`, which stays `float("inf")`. The
freshly-extracted bounding helper passed that into `Thread.join(timeout=inf)` →
`OverflowError: timestamp too large to convert to C _PyTime_t`. Because the tool catches LLM
failures and prints them as a note, it still emitted a normal-looking report with its
LLM-suggested candidates silently absent — so its headline answer ("no working replacement
found") was wrong, and nothing looked broken. The whole terminal gate missed it because every
probe drove the cron path.

- **Enumerate a skill's entry points in Phase 0** (`SKILL.md` usually lists them: the cron
  script, each documented CLI invocation, any `--flag` mode) and run each one at least once
  before declaring a shared-helper refactor done. `grep -rn "import <shared_module>\|from
  <shared_module>"` to find every consumer.
- **A sentinel default that is `inf`/`None` is the hazard.** Make the helper tolerate an
  un-armed value (clamp to something finite and bounded) rather than trusting every caller to
  initialize it — a library that only works when the caller remembers a setup step will meet a
  caller who doesn't.
- **Tell:** a tool that reports a *degraded* result through a caught-and-logged path. Grep the
  run output for "failed", "unavailable", "skipping" even when the exit code is 0 — a report
  that printed is not a report that worked.

## Bug-classes from the spotify-playlist-refresh 2.17 tune-up (2026-09-23)

- **An inferred quantity built on an UNVERIFIED timestamp semantic — the whole signal can be shifted by one row.** The poller inferred listen time as `min(dur_i, played_at_{i+1} − played_at_i)`, assuming Spotify's `played_at` is a play's *start*. It is the *end*. Every track was credited with the NEXT track's listen time — for four months, 1,547 of 3,522 events — and because the blocklist is permanent, **6 of 6 bans** were false (single "hard skips" that were full listens). Code review alone never questioned it; one query settled it. **Probe:** over consecutive event pairs with distinguishable durations, count how often the gap matches the *current* vs the *next* item's duration (911 vs 11 here); cross-check a track that's always followed by itself (BILLIONAIRE: gap ≈ own duration + a constant ~460 ms). Run this for any "derive X from gaps/deltas between timestamps" logic. **Fix shape:** flip the formula, take the oldest event's predecessor from the DB, recompute history with a one-shot migration (backup first) — and any *permanent* state derived from the bad signal (bans, "never again" lists) needs an explicit remediation decision, which is the **user's call** (ask; don't silently unban or leave it).
- **An "only ever move in one direction" upsert rule encodes the old semantics.** The cross-poll correction only ever *lowered* `ms_played` ("a later gap is authoritative and only corrects downward"). Under the corrected semantics the right values are often *higher*, so the rule would have silently blocked the fix. When you fix a semantic bug, re-derive every invariant that was justified by the old semantics (the refuter caught this one).
- **Sample-then-filter = silent underfill.** Discovery drew its 12 weighted picks from the raw candidate pool, then the live/instrumental/album-exclusion filters and per-artist caps dropped 4–9 of them with no refill; fallback padded the playlist with already-liked tracks. The dry-run *section breakdown* (24 core / 3 discovery / 1 wildcard / 11 fallback) was the tell — the total (39/40) looked almost fine. **Fix:** filter at ingestion, then pick through a weighted *order* with a cap-aware picker that skips and tries the next candidate (one shared picker so combined caps and dedupe are enforced across sections). Also watch for the fallback's supply ceiling: if fallback can only draw from the ~N items the scorer saw, it can never reach the target when N < target.
- **A cumulative-weight sampler that `continue`s on an already-picked item over-picks its neighbour.** `for i, cw in enumerate(cum): if r <= cw: if picked: continue` falls through to the NEXT index instead of redrawing. Use an exact without-replacement method (Efraimidis–Spirakis; sort by `log(u)/w` — `u**(1/w)` underflows to 0 for tiny w and ties back to input order).
- **Cache TTL == job period ⇒ effectively uncached.** A 24h artist cache read by a daily cron expires seconds before each run (start-time jitter decides hit or miss). Set TTL comfortably above the period (1.5×). Related: a refetch that *partially* failed (albums OK, album-tracks rate-limited) counted as success and overwrote a good row with an empty one "fresh" for the next TTL — only cache a fetch that was *complete*, and reuse the stale row otherwise.
- **A migration's "already ran" marker created BEFORE its transaction commits blocks it forever on a failed first run.** The first cut used the pre-migration DB backup file as the marker; a `database is locked` mid-run left the marker and every re-run skipped the ban lift. Put the marker in the DB, written in the same transaction as the change; make `--dry-run` create nothing (not even the marker table); refuse a non-existent `--db` path (sqlite3.connect happily creates an empty DB).
- **Stage budgets: a logging-only call that shares the essential write's budget can starve it.** Gate lap 1 found the snapshot-ID GET (used only for a log line) could burn the 150s write budget on timeouts so the playlist PUT never ran. Give each stage its own deadline (poll / compose / logging GET / write), sum them under the watchdog with slack for pre-stage work, and reset the deadline in a `finally` so it doesn't leak to later callers in the same process.
- **A new fail-fast threshold stricter than baseline turns recoverable waits into alerts.** Failing any `Retry-After > 30s` immediately (to stop sleeping through bans) regressed a 45s wait the old code survived. Fail fast only when the wait doesn't fit the remaining stage budget; in unbounded mode keep the baseline's per-sleep cap. A breaker tripped in one stage must not veto a later stage whose budget could absorb the wait (logged as a LOW follow-up).
- **Virtual-clock probes that rewind time break monotonic state — that's a probe artifact, not a bug.** A request pacer (`last_at + interval − now`) computed a huge sleep after the probe reset the fake clock to 0. Reset such state between probes (and skip pacing when the interval is 0) before concluding the code regressed.

Run it several times — a check that fails 1-in-2 is a timing bug, not noise.

## Bug-classes from the vault-audit 1.3 tune-up (2026-10-02)

- **"Couldn't read the ground truth" collapsed into "the ground truth is empty" — feeding a DESTRUCTIVE cleanup.** `gt_crons()` returned `[]` for a missing/unparseable `jobs.json`, so the orphan-cleanup step saw every `cron/output/<id>/` as orphaned and the unattended `--fix` rmtree'd all 25 (plus non-job dirs like `.git`), reporting "✅ Auto-fixed". The triggers were not exotic: Hermes's own loader accepts a bare JSON list and raw control characters (`strict=False`), which a strict `json.load` rejects. **Fix shape:** three-valued truth (unknown ⇒ one review item, every dependent check skipped); parse as leniently as the PRODUCER does, but all-or-nothing (one entry without a clean id ⇒ unknown — acting on "the rest" orphans live jobs); act only on names of the exact expected shape; refuse a bulk result (> max(3, 25%)); quarantine instead of delete. Tell: a `except: return []` reader whose result feeds a delete/move. (Sibling of *not-found conflated with error* and the three-valued health check — here the cost is data, not a false alarm.)
- **`shutil.copy2` carries the source's old mtime onto the backup — and an mtime-based prune in the same run deletes it.** The "back up first" invariant failed exactly for the stalest notes (5 fixes → 3 backups on the Pi; the previous Sunday lost 2). Use `shutil.copy` (fresh mtime) and prune by the timestamp in the backup's NAME, never this run's. Tell: `copy2` + `getmtime(p) < cutoff` in the same file.
- **A realpath containment check against a base that isn't realpath'd rejects everything the moment the path has a symlink.** `_vault_path` compared `realpath(VAULT/rel)` with an unresolved `VAULT`; under a symlinked home every read "escaped the vault", 7 of 12 checks returned silently, every fix was refused, and the VIP check emitted 5 false findings — a wrong report that looked normal. It surfaced only because the offline review kit lived under macOS's `/tmp` (a symlink). Realpath the base once; and make each check that depends on a note report "not verified" when it can't read it.
- **An auto-fix that rewrites the machine token but not the human copy of the same fact leaves a self-contradiction the audit then calls clean** ("Tue/Wed/Thu 07:28 (`25 7 * * 2,3,4`)"). And the follow-up trap the gate found: a review that fires only on the run that changed something ("expr fixed, but the time couldn't be") vanishes next week while the contradiction stays. **Never half-apply a fix:** when the companion can't be fixed safely, apply nothing and keep the item in review until a human fixes it. The same applies to the prose AROUND a token: an expr fix that changes the day fields (`30 10 * * 0` → `30 7 * * *`) leaves "Sun" wrong, and one that changes the hour field leaves "every hour, 24/7" / "08-21" / "every 2h" wrong (two successive gate laps) — auto-fix only when every human copy of the changed fields can be rewritten too (same days, and a fixed time whose HH:MM you rewrite, or a minute-only change), and send the rest to review.
- **Markdown-table parsing oscillated across three gate laps — what finally held: each row belongs to its NEAREST preceding header, and there is NO positional fallback.** `cells[2]/[3]` broke on `\|` or an added column; lap 1's per-header columns let an unrecognised header fall back to the default layout and edit another table's cells (both lap-2 lenses); lap 2's "first qualifying table" picked a template inside a code fence or a retired table above the real one (lap 3). lap 3's "nearest preceding header" recognised only `|---` separators, so valid GFM delimiters (`|-|-|`, `|:-:|`, `---|---`) let a history table inherit the jobs header, while a bare `---` rule under the last row swallowed it (lap 4). Final rule: a header is the line above a full GFM delimiter row, a heading/prose line ends a table, fences follow CommonMark, and rows under a header without the expected columns are not ours — never checked, never edited; and the expr is the ONE cron-shaped token in the cell, never "the first `(`…`)` span" (a decoy `(`after <id>`)` would have been overwritten — that one was pre-existing).
- **Data-driven (learned) regex rules need their own guards.** (a) A capture group outside group 0 (a lookahead `x (?=(\d+))`) made the splice insert text every week (`600300` → `600600300` …): require the group inside the match AND re-run the anchor on the edited text and require it to read the truth. (b) Python's `re` can't be interrupted (no timeout, signals aren't checked mid-match), so a catastrophic pattern hangs an unattended run until the watchdog SIGKILLs it with nothing reported. Static detection is a losing game: a string heuristic missed real shapes and refused safe ones; a parse-tree star-height check (`re._parser`) still missed a bounded repeat around an unbounded one and every *polynomial* shape (`\w+.*\w+.*\w+.*` >60 s on an 8 KB note). The fix that holds: evaluate user-supplied regexes in a child process with a timeout (`subprocess.run([sys.executable, __file__, "--_eval-…"], timeout=…)`, findings back as JSON) and report a timeout; keep the static check only as a learn-time refusal. (c) A secret filter that checks name SUFFIXES (`KEY`/`TOKEN`) is bypassed by `GITHUB_TOKEN_RO`, `SLACK_WEBHOOK_URL`, `headers.Authorization`, a trailing space — require a plain dotted path and match credential words anywhere; never silently drop a rule the filter catches (say so in the report).
- **A "seen N times" signal counted per RUN is inflated by bursts of manual runs — and the inflated number was used to justify a design change.** Five on-demand runs in six minutes made a finding "recurring (7x)", and the agent cited it ("flagging these same orphans for 7 straight weeks") when proposing the auto-delete change the user then approved. Count distinct days (or only scheduled runs).
- **A `deliver: local` job that exits 1 for "review items exist" and runs `--quiet` leaves useless archives:** normal weeks read "script failed / exit 1" with no content, weeks that edited notes read "silent". For `deliver: local` the scheduler only SAVES stdout — drop `--quiet` so the saved output is the record, and reserve non-zero for real failures (failed post, crash).
- **The agent changed the skill and nothing recorded it.** An on-demand session patched the live engine in five in-place edits (one transiently removed the `do_fix()` call), tested by creating a dir in the real `cron/output`, and added no version/changelog/doc change — so every doc kept saying the opposite ("review-only, always human-confirmed"). Only usage forensics (and the file mtime vs the last CHANGELOG date) revealed it. The intent is still the user's: read the session to establish what they approved before "reverting to the docs" (a forensics reviewer misread it as a one-off request; the approving question had been filtered out of the export because it didn't mention the skill's name — export whole sessions, not only matching messages).
- **Harness traps from this tune-up:** a UTF-16 split test that measured the output with the ENGINE's own `_u16` passed when `_u16` was mutated to `len` (measure independently); a suite that stubbed only `_post_chunk` would have reached Discord after a trivial refactor (stub `urlopen` too, use a dummy channel id in fixtures); `open(p, "w").write(open(p).read()…)` truncates before it reads; a suite whose fixtures use `tempfile.mkdtemp()` with no cleanup leaked ~15k throwaway homes into the Mac's `$TMPDIR` and 940 (≈150 MB) into the Pi's `/tmp` over one day of staging + mutation runs — put every fixture under one root removed by `atexit` (chmod back first, tests leave dirs unreadable), and check `/tmp` after the first staged run; and reviewers ran the posting wrapper unstubbed twice (one POST went out with the kit's fake token and was blocked by the sandbox proxy; the other hung before reaching the post) — say "stub `urlopen` in-process" explicitly in every reviewer prompt and keep only fake tokens in kits.
