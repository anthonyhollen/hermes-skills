# Hermes Skill Tune-Up

A repeatable method for improving an existing Hermes skill: hunt bugs, speed it up, shrink its token footprint, and make its delivery reliable — without breaking it, following a fixed sequence (preconditions → code passes → terminal gate → docs last). Distilled from many real tune-ups (task-tracker, email-gmail-triage, sg-commute, sg-car-plate-range, traffic-camera, spotify-playlist-refresh, hermes-backup, food-recommender, google-route-map, vault-audit, warframe-scraper, cc-bill-review, morning-brief, foodpanda-expense-tracker ×2, email-gmail-triage ×2, sg-commute ×3, discord-table-format, cc-bill-review ×2, vault-audit ×2, …) plus repeated **self-tune-ups** that re-sequenced the method itself. Each tune-up's bug-classes, perf levers, token techniques, and delivery patterns live in `references/`; **`CHANGELOG.md` holds the full per-skill provenance** — read it for the war story behind any rule.

## When to Use
- "review / debug / find bugs in the **\<name\>** skill"
- "make **\<name\>** faster / it's slow / it hangs / times out"
- "**\<name\>**'s SKILL.md is bloated / reduce its token usage"
- "**\<name\>**'s Discord delivery is unreliable / images missing / wrong order"
- A skill misbehaved in a live run and you want it hardened.

Not for: writing a new skill from scratch (`hermes-agent-skill-authoring`), or reviewing an arbitrary code diff (`requesting-code-review`).

## How a tune-up runs (the sequence)
The order is load-bearing: it keeps preconditions **universal** and the heavy validation **terminal**, so no late edit ships unreviewed and no doc goes stale. Run it in this order regardless of which passes the user asked for:
0. **Preconditions** — always, even for a single-pass request (below).
1. **Code passes** — Bug hunt → Performance → Delivery reliability. *All* behavioral/code edits happen here, on the live copy; keep docs *accurate* per change (safe-edit §5).
2. **Terminal validation gate** — fan out reviewers + diff the baseline over the *cumulative* **code** diff. **Re-entrant:** a regression it finds is itself a code change → fix it, re-sync that fix's docs, and re-run until a clean pass changes nothing. Only then is the code truly frozen.
3. **Docs pass, LAST — after the gate** — Token-efficiency relocation/slimming + the final doc-sync, on now-frozen code, so a relocated/slimmed doc can't end up describing code a later gate-found fix changed.
4. **Finish in sync, then clean up** — see *Always finish a tune-up with*.

## Phase 0 — Preconditions (always, before any pass)
Do these for **every** engagement — even "just make it faster" or "just slim the SKILL.md". Skipping them is how you optimize/slim/rewrite a copy that doesn't run, or ship a change with nothing to diff against.
- **Find the copy that actually runs.** A `no_agent`+`profile`-unset cron runs `~/.hermes/scripts/X.py`, not the skill-dir copy — they drift. Resolve the live path (`hermes cron list` / `~/.hermes/cron/jobs.json` → `script`+`profile`), `diff` it against the skill-dir copy; if they differ, consolidate first (that divergence is bug #1). For an *interactive* (non-cron) skill there's no `jobs.json` entry — the live copy is whatever `SKILL.md` tells the agent to run (commonly `~/.hermes/scripts/X.py`). Every later step — profiling, slimming, rewriting — targets the **live** copy. (Formerly Pass-1 Step 0; hoisted here because *every* pass needs it, not just the bug hunt.)
- **Run the no-LLM auditor on the live copy:**
  ```bash
  python3 ~/.hermes/skills/software-development/hermes-skill-tuneup/scripts/skill_audit.py \
          ~/.hermes/skills/<category>/<skill-name>
  ```
  It reports the SKILL.md token budget by section (code-fence-aware — `##` inside a ```` ``` ````/`~~~` fence isn't counted as a section), reference-link integrity (backticked **and** markdown `[text](…)` links; a trailing `--flag`/`#anchor` is stripped before the exists-check), frontmatter issues (incl. `description: >`/`|` block scalars), script anti-patterns (hermes-send, `MEDIA:` delivery, a subprocess call with no `timeout=`, token-from-env — docstrings/comments skipped via the Python tokenizer so example code in docs isn't flagged), SKILL.md duplication, and stray files (`*.bak` **and** the dated `*.bak-<tag>-<date>` convention). `--json` to consume programmatically. **Coverage caveat:** the anti-pattern scan only reads the skill-dir `scripts/`. A skill whose code lives in `~/.hermes/scripts/` (the live copy — common for interactive skills *and* `no_agent` crons) has **no** skill-dir `scripts/`, so the scan finds **nothing** — a *false-clean*. The auditor **warns whenever 0 scripts were scanned** (and now distinguishes "only the auditor's own source was here" from a real false-clean) and accepts `--scripts <dir>` to point the scan at the live code (e.g. `--scripts ~/.hermes/scripts`); otherwise review those scripts by hand. **Scope `--scripts` to the skill's OWN live code, not the whole shared dir** — `--scripts ~/.hermes/scripts` scans *every* skill's cron scripts and buries this skill's findings under other skills' anti-patterns; for a skill whose live copy is a byte-identical skill-dir `scripts/` copy, use the **default** scan (no `--scripts`), and reserve `--scripts` for a skill whose code lives *only* in `~/.hermes/scripts`, pointing it at that skill's file(s) where possible.
  - **The anti-pattern flags are line-local heuristics — eyeball each before "fixing" working code.** The scan downgrades a `DISCORD_BOT_TOKEN`-from-`os.environ` HIGH to **CHECK** when the file also reads `~/.hermes/.env` (the recommended fallback), and flags a subprocess call only when it has *no* `timeout=` (a hang risk, paren-balanced per call); whether a set timeout's `TimeoutExpired` is caught is left to the human bug-hunt. A `MEDIA:<path>` on a *legitimate* no_agent-deliver/terminal path is still HIGH **by design** (valid there — `references/delivery-reliability.md`); the file-open MED can't see a surrounding `try/except`. Confirm each flag against the live path; do **not** churn behavior-validated code to appease the linter.
- **Enumerate and exercise EVERY entry point, not just the cron path.** `SKILL.md` lists them (the cron script, each documented CLI invocation, each `--flag` mode); run each once before and after. A tune-up that only drives the scheduled path will ship a refactor that breaks an on-demand tool — and such a tool typically catches its own errors and prints a normal-looking, silently degraded report, so nothing looks broken (see the shared-state bug-class in `bug-hunt.md`).
- **Capture a green baseline.** Record what "working" looks like *before* touching anything, so the terminal gate has something to diff against: run the skill's regression suite if it ships one (note baseline-green), else hash an output fingerprint of the live dry-run (`--json` / `--dry-run`). **For a *scheduled* skill, also capture the baseline from archived trigger-time cron outputs** (`~/.hermes/cron/output/<job-id>/`), not only a fresh off-schedule run — a time-relative output looks right off-schedule and wrong on-schedule (see the Golden Rule). A tune-up with no baseline can't prove it didn't regress.

## The work passes
Run the passes the user asked for (or all for a full tune-up), in the sequence above — **code passes first, the docs pass last**. Each has a checklist + worked examples in its reference; read it before that pass. (The reference files keep their original *Pass 1–4* identifiers — bug=1, perf=2, token=3, delivery=4 — but the **execution order is the sequence above**: the delivery rewrite runs *before* the token/docs pass, so "Pass N" names a pass, not its position.)

**Code passes — all behavioral edits, on the live copy:**
- **Bug hunt** → `references/bug-hunt.md`. Read SKILL.md + every script + its dependencies and **validate against live data** (run dry modes, feed edge cases). Targets silent data drops, swallowed subprocess failures, uncaught timeouts, premature cleanup, dead code, unguarded file loads, shared helpers that misalign silently, **inferred signals built on an unverified timestamp/unit semantic** (probe the data — spotify's `played_at` was the play END, shifting every listen time by one row), **sample-then-filter underfill**, **a report scheduled before its own window's data lands** (compare each archived report's total against the current data — foodpanda's Sunday report never contained Sunday), **per-partition fixed costs that grow into a fixed deadline**, and — for an interactive skill — **a prose procedure the agent re-implements every run** (mine the `state.db` session history: task-tracker's hand-written atomic writes broke 8× in 39 uses) and **its compliance rate** — the output the skill should have produced vs what was actually sent (discord-table-format was loaded in 14 of 200 sessions; 213 raw markdown tables went out, because its "auto-load" frontmatter key is read by nothing). For a skill that **deletes or rewrites unattended**, check that an *unreadable* ground truth can't masquerade as an *empty* one (vault-audit's `--fix` would have moved every cron output dir on a bare-list `jobs.json`). For a **shared helper**, validate under every interpreter its consumers use and check its import side effects on them (a module-level `sys.path.insert` silently downgraded callers' requests/urllib3/certifi).. For a scheduled skill, **tally the archived outputs against the user's complaint history** — morning-brief's "green" runs were quietly short 4 of 12 times — and **re-measure any threshold its docs call "validated" over a full captured input** (capture one real input on the host, replay it offline). **read each value's own metadata before labelling it** — its validity window (sg-commute's "6–8am" line showed a 6pm→6pm forecast), its unit/interval (a 5-minute rain total labelled with hourly bands), whether it is one snapshot of a history (flood alerts counted ×25), whether the API pages (a 500-row cap hid 2,100 rows); for an interactive skill, **check the agent can actually read the results** (rows only in PNGs → the LLM misquoted counts) and that no doc teaches it to hand-roll the outward action (a curl recipe got the bot token printed into `state.db`). For a skill that turns a user's free-text reply into an irreversible action, **make the parser fail CLOSED** (refuse anything outside a strict grammar; the user's real replies from `state.db` are the must-still-work set) and bind "all" to what was actually *delivered* in that thread (cc-bill-review: "approve all except #18" approved #18). For a financial/inventory parser, **find the document's own reconciliation identity** (previous total + items == new total) and run it over the stored data — it falsified a "page-break duplicate" display filter that hid double charges, and it is the best completeness check. **Check every test fixture's data SHAPE against what the real API returns** — email-gmail-triage's idempotency guard compared label *names* against Gmail's label *IDs* and was dead for months while its test (fixture: names) passed. The bug hunt **fans out independent blind reviewers to *find* bugs** (distinct lenses + an adversarial refuter, triage by agreement) — separate from, and in addition to, the terminal gate that re-reviews the shipped diff.
- **Performance** → `references/performance.md`. **Profile first** (`time.perf_counter`, `-X importtime`), **cold *and* warm** (first run is disk-bound on the Pi); fix the real bottleneck, not the cheap parts. Usual culprits: repeated process spawns / sequential network calls — or, for DB-backed skills, full scans + per-row Python parsing (push filters into SQL). **Coupling to respect:** "replace the CLI delivery with `curl`" is *both* a perf lever and the delivery rewrite — do it under Delivery so its safety rules travel with it; never ship a bare `curl` from the perf pass.
- **Delivery reliability** → `references/delivery-reliability.md`. For Discord, **never** use `hermes send` / `MEDIA:` tags (PATH-fragile + `extract_media()` reorders). Use direct REST multipart (content+file in one `curl`), token from `~/.hermes/.env`. This pass **owns** the CLI→`curl` rewrite — including content limits + untrusted-field sanitization — wherever it was motivated (incl. from the perf pass). A script that posts its own content (the `--post` path) prints ONE line written for the user (the agent's whole reply), never an instruction to the agent, and nothing on stderr. Failure handling goes in SKILL.md, keyed by exit code. (`--dry-run` / print-only output meant for the agent is a different contract.)

## Terminal validation gate (over the cumulative code diff — before docs)
The heavy validation is **terminal**, over the *cumulative* **code** diff of every pass — not scoped to the bug hunt. Your last-edited code (a perf refactor, a delivery rewrite) is the least-reviewed in the repo, so review the whole shipped diff together. Mandatory for **every** engagement that changed code — including a perf-only / token-only / delivery-only one.
- **Fan out independent blind reviewers over the cumulative diff** — diverse lenses + an adversarial refuter — to hunt regressions *your own* edits introduced, not just the original bugs (a real tune-up's fan-out caught a regression the author's fix introduced). Protocol in `references/bug-hunt.md`.
- **Diff against the Phase-0 baseline** / re-run the regression suite **on the deployed copy**; for a behavior-preserving change confirm the output fingerprint is unchanged, for a perf change measure *success*, not just wall-clock.
- **The gate is re-entrant — loop to a fixpoint, and budget for MORE than one lap.** A regression it finds is itself a code change: fix it, re-sync *that fix's* docs (safe-edit §5), and **re-run the gate** until a clean pass produces no new edits. In the morning-brief tune-up the gate ran **four** laps and every lap found a real regression in the *previous* lap's fix — including a HIGH where the fix for a concurrency bug lost 7 of 8 LLM summaries, and three successive "the timeout is now bounded" fixes that each left a different hole (see `performance.md`). Treat one clean lap as the exit condition, not one lap.
- **For a skill that CURATES content, one gate reviewer must be an editor** — replay captured real inputs on a frozen clock and judge every pick against its section's promise (morning-brief 1.10 passed ten code-correctness laps and still shipped a worse brief; `bug-hunt.md`).
- **Stateful, multi-day heuristics need a multi-day simulation harness, and oscillating laps mean SIMPLIFY.** morning-brief 1.10's hold-back ran **10** laps; laps 3–9 each found a MED+ problem in the previous fix, visible only in a 10-day simulation with injected repeats/follow-ups. When each fix of a heuristic opens a new hole, remove the clever part and document the residual limit (`bug-hunt.md`).
- **A comment that asserts a bound is a CLAIM — test it, and fix the comment when it's wrong.** The same skill shipped three consecutive docstrings stating that a dripping provider could no longer overrun the step budget; each was false, and each made the next reviewer's job harder by manufacturing false confidence. When a fix's own comment says "this is now impossible", write the probe that tries it, and if you loosen the fix later, correct the comment in the same edit. (Sibling of *the skill's OWN references can be wrong and mislead the fan-out*.) Only a clean pass means the code is truly frozen — and only then do the docs (below) describe final code. This is why the docs/token pass runs *after* the gate, not before it.
- **Validate outward actions without spamming** — read-only probe (`GET /channels/{id}`), then **ask before a live send**.
- **Mutation-check every lap's new tests against the PREVIOUS lap's code** — each new check must fail there; foodpanda's lap 3 caught two vacuous checks this way.
- **A reader/writer protocol change (watermark, cursor, ledger) gets a randomized interleaving simulation built on the REAL functions**, run for every starting state including the *legacy* on-disk format the deploy will meet — email-gmail-triage's lap 2 found duplicates in 12k/20k interleavings that no hand-written case hit.

## Docs pass — runs LAST, after the gate
Run the token-efficiency relocation/slimming + the final doc-sync **only once the gate is clean** (true code freeze), so a relocated/slimmed doc can't end up describing code a later gate-found fix changed — the *relocated-copy-goes-stale* miss this skill hunts. Pure doc surgery doesn't need the fan-out; it's validated mechanically by the closer's auditor + whole-dir `grep -rn` (see *Always finish a tune-up with*).
- **Token efficiency** → `references/token-efficiency.md`. `SKILL.md` loads on every trigger; the `description` is always-on. **Relocate** reference-only content (changelog, recovery data, verbose mechanics, big examples) into `references/` + `CHANGELOG.md` — append unique blocks (don't delete), pointer-replace duplicated ones, then verify nothing was lost. Keep SKILL.md = triggers + operations + a References table. If the skill **calls an LLM per item** at runtime, the reference also covers trimming that prompt (drop unused fields, cap input per task type, `max_tokens` doesn't bill).

## Editing Safely
Skills live outside git, so follow `references/safe-edit-workflow.md` for **every** change: back up before overwrite → edit locally & push over SSH → restore mode 600 → `py_compile` + dry-run **with the gateway venv interpreter** (`~/.hermes/hermes-agent/venv/bin/python` — not system `python3`; imports differ) → validate outward actions **without spamming** (e.g. `GET /channels/{id}`, ask before a live send) → change cron config with `hermes cron edit`, never hand-edit `jobs.json` → bump `version` + add a `CHANGELOG.md` entry → delete backups only after the user confirms a live run.

## Always finish a tune-up with (required)
A tune-up is not done until **both** of these are met:
1. **Sync the target skill's docs to the code you just shipped.** Re-sweep its `SKILL.md`, `CLAUDE.md`, and `references/` for doc↔code drift your fixes introduced (changed constants, renamed/removed functions, altered flow, new behavior) and correct every stale claim — grep the docs for the old values/names. The docs MUST match the shipped code; doc↔code drift is itself a bug-class this skill hunts (Pass 1), so never leave new drift behind. For dated historical/diagnosis docs, add a dated correction note rather than rewriting the record.
2. **Feed new lessons back into THIS skill.** Every new bug-class, failure mode, or method refinement you discover MUST be written into the relevant `references/` file (and noted in this skill's intro + `CHANGELOG.md`) before you finish — so the next tune-up starts from it. A pass that found something new but didn't record it here is incomplete.

**The closer audit is expected to be a little noisy — that doesn't block "done".** Your in-flight `.bak`/`.bak-<tag>-<date>` backups still appear under `[STRAY FILES]` (they're deleted only *after* the user confirms the live run), and a deliberately-deferred token relocation still shows as `LARGE-TRIM`. Neither is a failure. Only **new dangling links, new anti-patterns, or unsynced doc↔code drift** block completion.

## Golden Rules
- **Preconditions are universal; validation is terminal.** Find the live copy + capture a green baseline before *any* pass (Phase 0), and fan out reviewers over the *cumulative* diff before declaring done — for **every** engagement that changed code, not just the bug hunt.
- **Freeze code before docs — and the gate decides when it's frozen.** Run the token/relocation pass only after the *terminal gate passes clean* (the gate is re-entrant: a fix it finds re-runs it), so a relocated/slimmed doc can never describe code a later gate-found fix changed.
- **Validate against live data, never code-reading alone** — every bug in the source tune-up was confirmed by running it on the real file.
- **For a *scheduled* skill, validate at its REAL trigger time, not a convenient one** — read the archived cron outputs (`~/.hermes/cron/output/<job-id>/`); a fresh off-schedule run can look perfect while the scheduled run is wrong (a time-relative output — forecast periods, "tonight"/"tomorrow", market/tide windows — shifts with the clock). Look for an internal-consistency *tell* (a datum contradicting its own label) rather than trusting the labels. (sg-commute: the morning report mislabelled every weather period; the tell was a "(Night)" code under a daytime label in archived 07:25 outputs.)
- **Never audit solo — spawn independent reviewers** (diverse lenses + an adversarial refuter): during the bug hunt to *find* bugs, and again at the terminal gate to re-check your *own* applied edits over the whole shipped diff; in real tune-ups the fan-out caught both bugs the author missed *and* a regression the author's fix introduced.
- **The skill's OWN references can be wrong and mislead the fan-out.** Blind reviewers read `references/` as ground truth, so a confidently-wrong doc note *manufactures agreement* against a true finding. When a reviewer cites a doc (especially one saying "verified") to REFUTE a live-confirmed finding, re-verify the doc against live data — and fixing the wrong doc (dated correction) is part of the fix, or it re-arms the same false refutation next time. (sg-commute: two blind reviewers refuted the real period-shift bug by citing a doc "correction" that had only eyeballed the labels.)
- **Measure before optimizing; don't optimize the cheap parts.**
- **A reliability fix that copies a proven sibling beats a clever new one** — `token-usage` and `sg-commute` already solved Discord delivery; reuse it.
- **A tune-up ends in sync** — the target skill's docs match the shipped code, and every new lesson is written back into this skill (see *Always finish a tune-up with*).
- **Leave the skill better documented than you found it** — version bump + changelog so the next tune-up starts from your findings.
