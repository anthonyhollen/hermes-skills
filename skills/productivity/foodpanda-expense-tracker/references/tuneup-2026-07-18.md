# Tune-up — July 18, 2026 (timeout & reliability hardening)

> **Correction (2026-09-28):** the no_agent script watchdog on this host is the global `cron.script_timeout_seconds` = **600 s** (config.yaml), not ~120 s. The "~120 s" budget math below was sized for a limit that didn't apply; v1.7.0 uses `RUN_DEADLINE_SECS = 300` — see `tuneup-2026-09-28.md`.


A full `hermes-skill-tuneup` pass run right after the Grab provider was added (same day), specifically to assess **yesterday's timeout-crash fix (2026-07-17)** and **today's new Grab code** for correctness, completeness, and robustness. Method: Phase-0 baseline → bug-hunt fan-out (3 blind reviewers) → perf/delivery → a re-entrant terminal validation gate → docs. Version 1.4.0 → **1.5.0**.

## Headline finding — the 07-17 timeout fix was CORRECT but INCOMPLETE

The 07-17 fix wrapped the one call that crashed (`get_all_sheets().execute()`) in `retry()` and made `retry()`'s pattern match case-insensitive (`"timed out"`). But:

- **`run_gapi()`'s `subprocess.run(...)` had no `timeout=`** — a hung `google_api.py` (Gmail search / `gmail get` / any sheet read via the CLI) would block until the **~120s cron SIGKILL**, which is uncatchable and posts **no** Discord alert. `retry()` can't help a call that never returns.
- **The direct googleapiclient calls were built with no HTTP timeout** — `create_month_sheet`, `ensure_provider_column`, `append_rows`, `update_sheet_row`, and `get_all_sheets` could each stall indefinitely.
- **`retry()` around an unbounded per-attempt call is worse than no retry** — 3 attempts × a long timeout + backoff can *exceed* the 120s watchdog, turning a fast catchable failure into a silent kill.

**Fix applied:**
- `socket.setdefaulttimeout(CALL_TIMEOUT=20)` at import — bounds every in-process googleapiclient/httplib2 socket (the clean lever when `build()` won't take a timeout).
- `run_gapi`'s `subprocess.run(..., timeout=CALL_TIMEOUT)` — a hang now raises `TimeoutExpired` (which `retry()` treats as transient).
- A run-global monotonic deadline `_run_deadline = time.monotonic() + RUN_DEADLINE_SECS(80)`, set at the top of `main()`; `retry()` checks it **pre-start** (no new call past the deadline) and **pre-sleep** (no backoff crossing it). Worst case = one in-flight call (≤`CALL_TIMEOUT`) after the deadline → `80 + 20 = 100s`.
- The **top-level crash handler now posts via `quick_alert()`** — a single `urlopen(timeout=8)`, **no retry** — instead of the retry-based `discord_alert`. A retry-storm alert (3× urlopen + backoff ≈ 60s) fired late in a run could itself be SIGKILLed, losing the only failure signal on a `deliver: local` job. Invariant: `RUN_DEADLINE_SECS + CALL_TIMEOUT + ~8s < 120`.

**Terminal gate caught a regression in this very fix (round 1):** the deadline was initially checked only *between* retry attempts, and the crash alert still went through the retry storm — so the worst case still breached 120s. The adversarial refuter reproduced the timeline (call issued at t≈95 → finishes ≈115 → +15s alert = ≈130 > 120). Round-2 added the pre-start/pre-sleep gates + the single-shot `quick_alert` and lowered the budget to 80; the re-run gate confirmed 80+20+8 = 108s < 120 (12s headroom) and no new regression.

## Other fixes (from the bug-hunt fan-out, ≥2-reviewer or cheap crash-hardening of new code)

- **Report-once alert re-fire (3/3 reviewers, MED).** A parse/foreign skip that sits *newer* than a still-retryable **fetch** failure can't advance the watermark past it, so the `⚠️ Unparseable` / `ℹ️ Non-SGD` alert re-fired every run until the transient cleared. Fixed with a persisted `reported_skip_ids` set (in state), saved **early** (before the `any_failure` guard) so "report once" holds regardless of watermark progress; bounded to the last 500.
- **`norm()` crashed on a currency-formatted legacy amount cell** (`float("$30.32")`). Now uses `parse_money` — currency-tolerant, and identical output on plain numerics (dedup unchanged).
- **`_parse_pickup_date` accepted impossible dates** (`31 Feb 26` → `2026-02-31` → later `sheet_month_name` crash) and truncated a 4-digit year to the wrong year. Now validates via `datetime(...)` and the Grab `date_re` ends with `(?!\d)`; both degrade to a clean parse-failure.
- **Merchant name interpolated raw into the Discord embed** — a provider-controlled field that could inject a masked link / break formatting. Now passed through `san()` (neutralizes backticks / `@` / `](` / `://`).
- **Crash traceback could exceed Discord's 4096-char embed limit** → the alert 400s and posts nowhere. Now truncated to the last 1500 chars.
- **Weekly showed `MTD Total: S$0.00` when MTD was actually unknown** — now shows `N/A` (removed the dead `mtd_val`).

## Follow-up (2026-07-19) — the tune-up shipped a regression; first cron run caught it → v1.5.1

The first scheduled run after this tune-up (2026-07-18 23:31) **failed** — but *cleanly*, exactly as the hardening intended: the `gmail search` subprocess hit the new `CALL_TIMEOUT`, `retry()` bounded + retried it 3×, and the crash handler posted an alert (no silent SIGKILL). Root cause: **`CALL_TIMEOUT=20` was set without measuring the call's real latency.** A cold `run_gapi(["gmail","search", after:2026/05/01, --max 50])` spawns a fresh interpreter + OAuth and **hydrates the full 50-message cap of historical receipts → measured 16–25s** — right at/over 20s, so a normal-to-slow night false-tripped it and all 3 retries timed out.

Fix (v1.5.1):
- **Narrow the search window to the watermark** — `after:<watermark.date − 1 day>` (behaviour-preserving: the loop already skipped `≤ watermark`; message-id dedup covers the overlap). The search drops from ~18s to **~2s** because it stops hydrating already-synced receipts. This is the real root-cause fix.
- **`CALL_TIMEOUT` 20 → 30, `RUN_DEADLINE_SECS` 80 → 75** (invariant 75+30+8=113<120) — headroom for a slow night and for the rare wide-window first-run backfill (~25s).
- **Friendlier crash alert** — `friendly_error(e)` posts a short plain-English cause (timeout / 429 / auth / …) + a "nothing saved, will retry" note; the full traceback stays in the cron log, not Discord (it used to dump the truncated traceback into the channel).

Verified: a live run completed in **2s**, exit 0, "No new receipts to process."

**Meta-lesson (written back to `hermes-skill-tuneup`):** when you add a timeout to a call, **measure that call's real cold latency first** — a timeout guessed from an assumption ("small emails are fast") can false-trip a legitimately-slow call, and here it did so on the very next unattended run. Offline import-tests and the gate's timing *math* both passed because neither measured the actual subprocess wall-time.
