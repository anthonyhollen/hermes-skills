# Tune-up — September 28, 2026 (v1.6.0 → 1.7.0)

A full `hermes-skill-tuneup` pass, one day after the monthly payment reminder (v1.6.0) was added by an agent session. Method: Phase 0 (live copies byte-identical ✔, auditor, archived-output tally of 50 sync + 22 weekly runs, a sandboxed read-only sync run) → bug hunt with 3 blind reviewers (control-flow/state, data-shape, ops/delivery/perf) + an adversarial refuter, all offline from a local kit → perf + delivery fixes → a re-entrant terminal gate (**3 laps**) → docs.

## Headline findings

- **The weekly report never included Sunday's orders** (HIGH, 3/3 reviewers + refuter, confirmed from the archive). It ran Sunday 09:05 for the *current* Mon–Sun week; Sunday's receipts only sync at 23:30 that night, and the next report starts Monday. 11 of 18 archived reports were short — **S$599.22** of Sunday spend since June never appeared in any weekly report. *User decision:* first Monday 09:05 for the previous Mon–Sun (1.7.0), then — same day, before it ever ran — **back to Sunday 09:05 for the previous complete Sun–Sat week** (1.7.1, `5 9 * * 0`; the user's reason was DeepSeek off-peak pricing, though these no_agent jobs make no LLM calls). MTD = the month the week ended in, through that Saturday. The last old-style report (Sun 27 Sep, Mon 21–Sun 27, contained only 21–26 rows) hands over cleanly to the first new one (Sun 4 Oct: Sun 27 Sep – Sat 3 Oct) — no gap, no double count.
- **Migration cost grew every month toward a silent stall** (HIGH, 3/3 + author). Every sync run with anything new spawned `google_api.py` twice per month tab for the migration checks — 18 of 27 spawns, ~17 of 28 s at 9 tabs, +~1.8 s/month — against a self-imposed 75 s deadline. Past the deadline even the alerts were refused (they went through the same `retry()` gate) and the run exited 0: no rows, no alert, no state, repeated nightly (onset simulated at ~15–35 tabs depending on latency, or today with a ~45-receipt backlog). Fixed with **one in-process `values.batchGet`** of every tab (**28 s / 27 spawns → ~10.5 s / 9 spawns**, same receipts/watermarks/writes on live data), deadline raised to 300 s, alerts not deadline-gated.
- **The "~120 s watchdog" was never real** — `cron.script_timeout_seconds` is **600 s**. The 120 s in the 07-17 incident was the OS TCP timeout. All budget comments/docs corrected.
- **Reminder `--simulate-date` without `--dry-run` posted live and cancelled the real fire** (2/3 + author): it marked the simulated cycle fired, so the real 1st-of-month run skipped. `--simulate-date` now implies `--dry-run` unless `--force`.
- **Reminder total could be short** (3/3 + author): orders after the month's last 23:30 sync would miss the 09:00 reminder. A catch-up sync at 08:45 on the 1st was added in 1.7.0, then **removed in 1.7.2 at the user's direction**: they essentially never order after 23:30, so nothing should be designed around it. What remains is the failure case: the reminder adds a heads-up line if the sync on the month's last night (or later) didn't finish OK (read from `jobs.json`).
- **Discord POSTs were retried after a read timeout** (2/3) → a POST Discord had accepted could be re-sent (double @-ping). `discord_send` now retries only 429/503/connect errors; the reminder also sends `nonce` + `enforce_nonce` (so it can retry 5xx safely).
- **Grab ride receipts raised false "Unparseable — format may have changed" alerts** (2/3 + author; confirmed: the 2026-08-19 alert's two ids were taxi rides). Now skipped silently (`nonfood_re`), only when the ride phrase is present AND there's no `Order from:` merchant.
- Smaller: `run_gapi` used a bare `"python"` (PATH-accident) → `sys.executable`; the non-gws `No messages found.` (non-JSON) crashed the documented manual-recovery path → `[]`; handled failures exited 0 (job stayed green) → exit 1; an impossible FoodPanda date would crash every run; an overrunning merchant capture (missing end label) → capped; the crash alert's "Nothing was saved" was false after a partial write → reworded; RFC 5322 Date variants (`(UTC)`, `GMT`) now parse.

## Terminal gate — 3 laps, each lap found holes in the previous lap's fixes

- **Lap 1** (regression lens + adversarial refuter): the author's **watermark hold on an unreadable Date** (added to make undated emails "retried, not lost") was a MEDIUM regression — in a 60-day simulation a permanently-undated email froze the provider for 49 days (1,285 vs 60 fetches, 49 daily alerts, a user-deleted row re-added). **Reverted** (simplify, don't add a rule) — the docs' "retried until fixed" claim was corrected instead, and header parsing broadened. Also: a false reminder caveat on days 2–5 (checked "today" not "since the 1st"); weekly MTD from `G2` counted days after Sunday; the batched migration skipped F1/G on a new empty tab in the same run; posts after the deadline could stack to >600 s in a contrived double outage; 502/504 retries could duplicate.
- **Lap 2** (adversarial): apostrophe-quoting only the batch read made a tab like `Anthony's notes` crash **every** sync (per-tab guard restores the old skip-that-tab behaviour); the reminder no longer retried a nonce-protected 502 (now `retry_ambiguous`); per-month post-deadline alerts → one combined alert and stop.
- **Lap 3** (self-probed with the reviewers' own simulations): 60-day undated sim identical to the original; watchdog worst case **360 s flat** for any month count (lap 1: 585 s; 13 months on lap-1 code: 993 s); apostrophe tab no crash; 14 caveat-timing cases correct. Clean.
- A new offline suite, `scripts/test_foodpanda.py` (60 checks, one per fix), was mutation-checked: each lap's new checks fail on the previous lap's code and pass on the final code. Two vacuous checks were caught this way and tightened.
