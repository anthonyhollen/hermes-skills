# Discord Image Delivery — how `nearest_carpark.py --send` posts (v1.11.0)

**Class of problem:** a report whose sections each carry an image (the parking table PNG, the EV table PNG, the static map) must arrive with each image in the **same Discord message** as its header, in order.

**Why a script, not the agent:** `send_message` with `MEDIA:` tags cannot pair text with images — the gateway's `extract_media()` scans the whole reply, sends all text, then all images, so order and pairing are lost. The only reliable pattern is one REST multipart POST per section (`payload_json` + `file`), which `--send` does. The agent must never re-implement it: in a 2026-07-16 session an agent hand-rolled the curl, `grep`ped `DISCORD_BOT_TOKEN` out of `.env` (the token then sat in the session log) and posted literal `\n`s. (The older hand-roll recipe and helper snippets that invited this are archived in `changelog.md` → *Relocated 2026-09-29*.)

## What `--send` does
1. **Resolve the destination before any API call.** Precedence: `--thread <id>` → `--send <channel_id>` → the conversation the agent is in: `HERMES_SESSION_KEY` = `agent:main:discord:<chat_type>:<chat_id>[:…]`, use **`parts[4]`** (never `parts[5]`, which is the user id for a plain channel). The gateway bridges each turn's `HERMES_SESSION_*` ContextVars into the terminal subprocess (`tools/environments/local.py` `_inject_session_context_env`, verified 2026-09-29), and every parking request so far ran in an auto-created thread whose key is `agent:main:discord:thread:<thread_id>:<thread_id>` — so plain `--send` lands in that thread, including for follow-ups deeper in it (a follow-up's *message* id is not a channel → 404, which is what bit the 2026-07-30 session). If `HERMES_SESSION_CHAT_ID`/`THREAD_ID` are also exported they must agree with the key's `parts[4]`, else it refuses. Unresolvable → exit 2, never a fallback channel. Ids must be ≥15-digit snowflakes (`<#id>` and `discord:id` are accepted); a 6-digit postal after `--send` is the address, while any other id-shaped token (≥7 ASCII digits, `<#…>`, `<@…>`, `discord:…`) that isn't a valid snowflake right after `--send`/`--thread` — or appears anywhere else in argv — exits 2 instead of silently becoming part of the address and posting to the session.
2. **Post** the title (`## :red_car: Parking Lot Report`), then one message per section: `**<header>**` + body (+ the section's PNG). Body text is sanitised (`_sanitize_discord`: newlines, backticks, mentions, masked/auto links) line by line, and `allowed_mentions: {"parse": []}` rides in the same `payload_json` (sent with `--form-string`, never `-F`, which truncates at `;`). Table sections normally have no body — the PNG is the table (the user removed "Total parking: N" text on 2026-06-01). If the table image failed to render, the body is `*(table image unavailable)*` + one text row per line.
3. **Retries are duplicate-safe:** each message carries a `nonce` (`sgc<run-id><index>`) with `enforce_nonce: true`, so a retry after a timeout/5xx whose first attempt actually landed returns the existing message instead of posting twice. curl has `--max-time 15`; a 429 waits `retry_after` (clamped to 0–30 s). The whole RUN must end with a printed verdict inside the agent's terminal timeout (often `timeout: 60`), because a killed run leaves a partial post and invites a duplicate re-run: the send deadline is 50 s after **script start** (`SEND_DEADLINE_S`), each curl's `--max-time` is clamped to the time left, no retry sleeps past it, and no message starts with <3 s left. 401/403/404, a 429 that outlasted its retries, or the budget running out stop the loop (every later post would fail the same way); any unexpected error also stops it and falls through to the exit contract below.
4. **Exit contract** (what the agent reads — also printed after an agent-only `AGENT DIGEST` of the rows):
   - all sent → `[SILENT]` + `Sent N/N messages to <id> (<how>)`, exit 0;
   - nothing sent → `DELIVERY FAILED: …`, exit 1 — "nothing was posted" + a hint for a definitive refusal (a 404 on an explicit id: "a MESSAGE id? re-run with plain --send"; a 429: "wait a minute, then re-run once"); **"nothing was CONFIRMED posted … check the conversation before re-running"** when any POST timed out or 5xx'd (it may have landed; a re-run gets new nonces);
   - some sent → `PARTIAL DELIVERY: … do NOT re-run`, exit 0 (a re-run would duplicate the posted part).
5. **Cleanup:** this run's PNGs (tables + the per-run map `/tmp/hermes_cache/carpark_map_<pid>_<ms>.png`) are deleted only after a full delivery; anything older than an hour is swept at the start of the next run (a wipe-all glob used to delete a concurrent run's images).

## Rules that still hold
- **Don't add summary text to the table sections** ("Total parking: N" was removed at the user's request). The LOCATION section's body is the resolved address — keep it.
- **Single source of truth:** terminal mode prints each section with `format_section_content()`, the same function `--send` posts, so the terminal text of a section is byte-identical to its Discord message. The `AGENT DIGEST` is a separate, labelled block that is never posted.
- **Threads are channels** in the v10 API — `POST /channels/<thread_id>/messages` posts into the thread.
- Test changes to the delivery path in **#playground** (`1501742338639401071`), never #alerts or the user's threads; prove a request shape without posting with a read-only `GET /channels/<id>`, or with a reject probe (empty content → 50006).

## Cron reports are different
The two `no_agent` crons don't self-post: they print, and the scheduler delivers stdout (the morning map rides a single trailing `MEDIA:<path>` line — legitimate there, because the scheduler attaches exactly that file; it does not check the bytes, so the script validates the PNG first).
